# Cycle 06: Automated Preflight Diagnostics - UAT

## Test Scenarios
The primary user acceptance testing scenarios focus specifically on proving the absolute robustness and flawless mathematical evaluation of the visual representations generated by the React Flow/Three.js frontend and their precise integration seamlessly into the highly specific preflight mechanisms natively required by the core engine. The UAT simulates the safe mathematical processing of a simplified spatial GUI representation perfectly. This cycle proves that the system protects the user from costly runtime errors through intelligent compile-time analysis and "run 0" simulations.

* **SCENARIO-06-A [Priority: High] - Successful Preflight Diagnostics Run (Clean Configuration):** The UAT must simulate a user completing the simplified configuration. The interface successfully receives a valid Intent payload with a structurally sound atomic system (e.g., a perfect FCC lattice) and valid file paths. The API explicitly correctly evaluates the entire configuration accurately, passing the preflight checks. The system returns the compiled `WorkflowConfig` ready for execution without generating any warnings or errors. This proves the system correctly identifies a physically valid intent. The simulated user sets up a standard active learning loop for Aluminium, utilizing default heuristics. The frontend submits the payload. The backend Semantic Compiler generates the `WorkflowConfig` and passes it to the `PreflightManager`. The `StructuralValidator` confirms the lattice parameters and interatomic distances are physically reasonable. The `DependencyValidator` confirms that the required default pseudopotentials exist in the specified directory. Finally, the `LammpsSyntaxValidator` executes a `run 0` command, confirming that the generated LAMMPS script initializes correctly without syntax errors. The API returns a 200 OK status, and the `DiagnosticReport` indicates zero errors and zero warnings, confirming the simulation is safe to dispatch. The test suite must rigorously assert that the returned `DiagnosticReport` JSON object contains empty arrays for the `errors` and `warnings` keys, and that the `info` array contains a single message stating "Preflight validation completed successfully." Furthermore, the test must guarantee that this entire compilation and preflight validation pipeline executes in less than 2000 milliseconds for a system of 100 atoms, proving that the synchronous "run 0" LAMMPS evaluation does not introduce unacceptable latency to the interactive React frontend experience. This performance constraint is crucial; if the preflight takes thirty seconds, the user experience of the GUI is ruined. The test will measure the execution time of the API endpoint using standard Python timing decorators and explicitly fail the UAT scenario if the threshold is exceeded, ensuring the `StructuralValidator` successfully utilized vectorized Numpy distance matrix calculations instead of slow Python loops.

* **SCENARIO-06-B [Priority: High] - Accurate Collision Detection & Rejection (Structural Failure):** The UAT tests that complex internal vector mathematical logic correctly identifies physically impossible atomic structures. An Intent payload containing an `ase.Atoms` object where two Platinum atoms are situated 0.1 Angstroms apart must trigger an immediate preflight failure. The API must return a detailed error pinpointing the indices of the colliding atoms, preventing the LAMMPS engine from instantly crashing. In this scenario, the simulated user accidentally imports a corrupted XYZ file where two atoms occupy nearly identical coordinates, perhaps due to a bad symmetry expansion or a copy-paste error during file creation. The frontend parses this file and submits the workflow payload to the backend compilation endpoint. The `PreflightManager` begins its sequence. The `StructuralValidator` analyzes the distance matrix of the provided `ase.Atoms` object. It immediately detects the unphysical overlap, calculating a distance of less than 0.5 Angstroms between atomic index 42 and atomic index 43. Recognizing this as a fatal flaw that will cause infinite repulsive forces in any classical potential or SCF non-convergence in Quantum ESPRESSO, the validator immediately halts the preflight process. It appends a critical error to the `DiagnosticReport`. The FastAPI endpoint catches this error state and returns a 400 Bad Request status code. Crucially, the JSON response must contain the `DiagnosticReport` with a specific, highly actionable severe error message: "Atomic collision detected between Atom Index 42 and Atom Index 43. Distance: 0.1A. Please relax the initial structure using a classical potential before initiating the active learning loop, or manually edit the input coordinates to remove the overlap." The React frontend will receive this specific message and is designed to display this error directly attached to the visual `INITIAL_STRUCTURE` node on the canvas. The test suite will meticulously assert that the returned JSON error array contains this string, and specifically checks that the correct atomic indices (42 and 43) are identified, proving the mathematical distance calculation correctly correlated the geometric flaw back to the exact atoms responsible, providing the user with pinpoint debugging accuracy.

* **SCENARIO-06-C [Priority: Medium] - Dependency Path Validation and Syntax Rejection (Missing Files & Bad Scripts):** The UAT will verify that if a user specifies an explicit path to a pre-trained MACE foundation model in the advanced settings, but that file does not exist on the server, the preflight diagnostic catches the error immediately. Furthermore, if the compiled LAMMPS script contains a syntax error (simulated via mock injection), the `LammpsSyntaxValidator` must catch it. The simulated user is attempting to fine-tune an existing model. They enter a custom, absolute path to a MACE model on the remote server via the React GUI's advanced settings panel: `/opt/pyacemaker/models/my_custom_mace_v2.model`. However, they have a typo in the filename; the actual file is named `my_custom_mace_v3.model`. They connect the nodes and submit the payload to the API. The `DependencyValidator` component of the preflight manager attempts to verify the provided path using synchronous `os.path.exists()` checks on the host filesystem. It fails to locate the file. It immediately appends an error to the `DiagnosticReport` stating "Required MACE model file not found at path: /opt/pyacemaker/models/my_custom_mace_v2.model". Concurrently, the UAT test suite will intentionally simulate an internal Semantic Compiler bug. It will inject a known, invalid LAMMPS command into the generated `WorkflowConfig` string—for example, inserting the command `fix 1 all nve_typo` instead of `fix 1 all nve`. The `LammpsSyntaxValidator` takes this flawed script, appends the `run 0` command, and attempts the dry-run initialization within the embedded Python LAMMPS library instance. The LAMMPS C++ core encounters the unrecognized fix style and throws a `LAMMPSException`. The Python wrapper successfully catches this exception, extracting the specific LAMMPS error string ("ERROR: Unknown fix style nve_typo"), and appends a second error to the report. The API returns a 400 Bad Request. The test suite will assert that the returned JSON payload contains two distinct errors in the `errors` array: one identifying the missing file, and one identifying the LAMMPS syntax failure. This comprehensive test proves the system acts as an impenetrable shield, comprehensively catching both environmental (missing files) and programmatic (bad scripts) failures simultaneously before a single computational cycle is wasted on execution.

## Behavior Definitions
These behavior definitions map to the exact User Test Scenarios, specifically defining the deterministic Gherkin-style assertions expected from the PyAceMaker Preflight module. This ensures the diagnostic logic behaves predictably and, providing clear error reporting to the GUI.

**Feature: Visual Configuration Semantic Compilation and Automated Preflight Validation**

**Scenario 1: Flawless Translation and Preflight Validation of Clean Geometry**
**GIVEN** the PyAceMaker Preflight module is fully active and configured
**AND** the simulated GUI perfectly specifically defines a structurally sound `INITIAL_STRUCTURE` with valid Cartesian coordinates and valid file paths
**WHEN** the simulated frontend connects passing through the compilation and preflight endpoint
**THEN** the API gateway responds immediately with a valid `WorkflowConfig` instance
**AND** explicitly the compiled `DiagnosticReport` effectively accurately contains zero errors perfectly successfully
**AND** the underlying LAMMPS `run 0` initialization test completes without throwing any syntax exceptions, confirming the system is fully ready to run the active learning loop.

**Scenario 2: Secure Detection of Atomic Collisions (Preflight Rejection)**
**GIVEN** the PyAceMaker Preflight module is fully active and configured
**AND** the user intentionally purely explicitly supplies a malformed structure with unphysical interatomic distances (e.g., overlapping atoms)
**WHEN** the simulated frontend sends a precise request
**THEN** the preflight diagnostic rigorously evaluates the pairwise distance matrix effectively accurately
**AND** automatically generates a critical structural error highlighting the specific atomic indices involved in the collision perfectly
**AND** the API gateway immediately returns an HTTP 400 Bad Request status code, halting the workflow before any execution or memory allocation occurs.

**Scenario 3: Correct Handling of Missing Dependency Files and Syntax Errors**
**GIVEN** the PyAceMaker Semantic Compiler and Preflight engine are processing a configuration payload
**AND** the user sets a visual node referencing a specific `.model` or `.UPF` file that does not reside in the server's working directory
**WHEN** the frontend submits the workflow payload for compilation and validation
**THEN** the preflight engine performs lightweight `os.path.exists()` checks on all referenced file paths
**AND** registers a "File Not Found" error in the `DiagnosticReport`
**AND** if the generated LAMMPS script contains a syntax error, the `LammpsSyntaxValidator` catches the `LAMMPSException` during the `run 0` dry-run
**AND** the final API response reflects both the missing dependency and the syntax error, returning a 400 Bad Request and allowing the React GUI to display explicit warning icons on the specific DAG nodes responsible for the failures.
