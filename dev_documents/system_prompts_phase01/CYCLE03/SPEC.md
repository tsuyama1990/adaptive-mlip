# Cycle 03: Spatial Tagging and ASE Integration

## Summary
The primary objective of Cycle 03 focuses precisely on explicitly bridging the complex gap between the spatial, 3D interactive bounding-box representations generated safely by the React Flow/Three.js frontend and the highly specific, text-based atomic tagging mechanisms native perfectly to LAMMPS (e.g., `region`, `group`, `fix`). This specifically requires the development of the `pyacemaker.utils.spatial` module and its strict flawless integration with the existing robust `ase.Atoms` manipulation logic.

By completing Cycle 03, the system mathematically enables non-expert engineers to simply "paint" or highlight regions—like the bottom layers of a complex metallic surface—and have the system accurately compile that visual intent directly into highly complex, valid LAMMPS physical simulation constraints. This completely eliminates one of the most error-prone aspects of molecular dynamics scripting: manually calculating and typing out Cartesian coordinates for spatial partitioning. The visual interface will transmit the start and end coordinates of the user's bounding box, and the spatial module will ensure that these boundaries are physically meaningful before translation.

This cycle represents a critical shift from abstract workflow configuration (handled in Cycle 02) to concrete physical state manipulation. The resulting spatial tags will dictate which atoms are allowed to move during the active learning loop, directly impacting the accuracy and computational cost of the simulation. The backend must guarantee that the selection masks generated are highly optimized and completely deterministic. This module ensures that the user's visual intuition is perfectly translated into the stringent mathematical rigor demanded by the underlying execution engines. Without this capability, simulating complex surface reactions or solid-liquid interfaces—which strictly require localized thermostats and frozen boundary layers—would remain inaccessible to the users of the Intent-Driven GUI. This feature effectively democratizes advanced molecular dynamics setup, transferring the burden of coordinate geometry from the researcher's brain to the computational backend.

The true value of this cycle lies in its ability to prevent simple coordinate typos from destroying a simulation. In traditional scripts, defining a `region` boundary incorrectly by 0.1 Angstroms might accidentally exclude a critical surface atom from the active learning loop, leading to an artificially stabilized, incorrect MLIP. By generating these boundaries interactively in a 3D viewer and mathematically mapping them via ASE, PyAceMaker entirely eliminates this class of manual error. The `spatial` module provides absolute confidence that the atoms selected on the screen are the exact atoms constrained during the molecular dynamics integration step.

## System Architecture
The implementation strictly aligns with the complete architecture mapping mathematical bounding parameters. We introduce `pyacemaker.utils.spatial` entirely. The `pyacemaker.utils.spatial` module acts as the pure functional mapping converting the abstract `gui_schema.SpatialRegion` objects precisely into mathematically correct `ase.Atoms.set_tags` commands.


The architecture strictly ensures that all spatial mathematics operate locally and securely on safe `ase.Atoms` exclusively in memory before committing to string-based LAMMPS outputs. The FastAPI endpoint will receive the spatial payload, unmarshal it into the appropriate `SpatialRegion` models, and pass these to the `spatial.py` utility functions alongside the initial structure loaded via ASE. This localized processing guarantees that no external dependencies or external state changes are required, maintaining the high performance of the web application. The design also permits future extensions, such as supporting spherical regions or complex polygonal selections, by simply expanding the functional logic within the `spatial` module without altering the core execution loops.

The architectural flow dictates that the Spatial Tagging module sits firmly behind the Semantic Compiler developed in Cycle 02. When the Semantic Compiler processes an `INITIAL_STRUCTURE` node that contains associated `SpatialRegion` definitions, it invokes the functions within `pyacemaker.utils.spatial`. These functions take the raw `ase.Atoms` object (which represents the initial physical state of the simulation) and the user-defined boundaries, applying Numpy-accelerated boolean masks to identify the specific atomic indices that fall within the painted regions. The architecture explicitly requires that this operation is completely stateless; the `spatial.py` module must not modify the original `ase.Atoms` object passed to it, but rather return a new array of integer tags or a securely copied instance containing the applied tags. This immutability principle is crucial for preventing subtle side-effects where consecutive compilation attempts might yield different physical results due to lingering state.

Once the integer tags are generated and verified against the boundaries, the Semantic Compiler resumes control. It is the responsibility of the compiler, not the spatial module, to translate these abstract integer tags into the concrete LAMMPS syntax. The compiler will map tag `1` to `region 1 block ...` and generate the subsequent `group` and `fix` commands required by the `LammpsDriverConfig`. By keeping the spatial logic strictly separated from the LAMMPS string generation logic, the architecture preserves the possibility of swapping out the molecular dynamics engine in the future (e.g., to GROMACS or OpenMM) without rewriting the core spatial mapping algorithms. This separation of concerns represents a highly mature software engineering approach to scientific simulation, ensuring long-term maintainability and extensibility of the PyAceMaker platform.

Furthermore, the architecture must account for the integration of these spatial regions with the active learning orchestrator. The `TwoTierEvaluator`—which determines when an atomic configuration requires DFT verification—must be aware of these frozen regions. Atoms that are explicitly frozen by the user should theoretically never exhibit high uncertainty because their positions do not update, and therefore they should be ignored during variance calculations to save time. However, if numerical noise causes a frozen atom to register an unphysical force, the evaluator must be able to ignore it based on its spatial tag to prevent spurious DFT calls. The architecture ensures that the integer tags generated in this cycle are seamlessly propagated through the PyAceMaker state machine, arriving safely at the evaluator logic and the Quantum ESPRESSO interface, guaranteeing physical consistency across all simulation phases. The entire system pivots on the absolute reliability of the `spatial.py` module's Numpy masking capabilities.

## Design Architecture
The `pyacemaker.utils.spatial` module exclusively houses the purely mathematical intersection algorithms cleanly. This layer effectively transforms correctly ordered boundaries explicitly (e.g., Z-min, Z-max) into `numpy` array boolean masks, precisely filtering `ase.Atoms.positions` cleanly. The design focuses on vectorization to ensure calculations remain instantaneous regardless of system size.

A key domain invariant dictates strictly that the `tags` property safely exactly on the `ase.Atoms` instance must specifically mathematically contain strictly valid positive integers cleanly. The mathematical mapping algorithm explicitly translates these integer tags precisely directly into purely matching LAMMPS groups seamlessly safely. For example, atoms tagged with the integer `1` might correspond to the `freeze_group` in the generated LAMMPS script, while atoms tagged with `2` represent the `thermostat_group`.

The design of the spatial utility functions focuses on utilizing vectorized Numpy operations to determine atomic inclusion within the bounding boxes. This approach avoids slow, iterative loops over atomic positions, ensuring that even systems containing millions of atoms can be tagged instantly during the compilation phase. The architecture requires that any atoms falling exactly on the boundary limit are definitively categorized (e.g., strictly inclusive on the lower bound, exclusive on the upper bound) to prevent non-deterministic tagging during floating-point rounding errors. This rigorous mathematical precision is vital for the integrity of the resulting molecular dynamics trajectory. The design mandates the use of `np.logical_and` across all three dimensions simultaneously to filter the coordinate matrix efficiently.

The fundamental design unit is the `SpatialRegion` Pydantic model added to `gui_schema.py`. This model must enforce stringent validation rules on the incoming visual parameters. It must guarantee that the `min` coordinate of a bounding box is strictly less than or equal to the `max` coordinate on any given axis. If a user maliciously or accidentally draws a bounding box with an inverted geometry (e.g., Z-min: 10, Z-max: 0), the schema validation must intercept this and immediately return a 422 Unprocessable Entity error before the payload ever reaches the spatial mathematical functions. The schema will also define an `Enum` for the specific physical actions the user intends to apply to the region (e.g., `ACTION_FREEZE`, `ACTION_LANGEVIN_THERMOSTAT`, `ACTION_ACTIVE_LEARNING_ONLY`), allowing the Semantic Compiler to correctly interpret the physical meaning behind the spatial tags.

The `spatial.py` module itself is designed as a collection of pure functions. The primary function, `apply_spatial_tags(atoms: ase.Atoms, regions: list[SpatialRegion]) -> NDArray[np.int_]`, will iterate through the defined regions and construct the corresponding Numpy masks. A critical design requirement is handling overlapping regions. The design must explicitly define the conflict resolution strategy. If an atom falls into two distinct regions painted by the user—for example, a `FREEZE` region and a `THERMOSTAT` region—the system must predictably resolve this unphysical contradiction. The design specifies a strict "last-writer-wins" or explicit priority ordering logic within the spatial module, ensuring that the final integer tag assigned to an atom is entirely deterministic regardless of how the user drew the boxes on the React canvas. This conflict resolution strategy must be well-documented within the code and presented back to the user via the API if a conflict is detected, as it directly impacts the generated physics simulation. The design favors failing fast (raising an error on overlap) over making assumptions, unless a strict priority hierarchy is mathematically defined and communicated.

The core implementation relies entirely on performing efficient matrix operations on the coordinates array provided by the `ase.Atoms.get_positions()` method to avoid any Python-level iteration over individual atoms.

Implement the core logic using stacked `numpy.logical_and` calls (e.g., `np.logical_and(positions[:, 2] >= z_min, positions[:, 2] < z_max)`) to efficiently determine inclusion across all three dimensions simultaneously in compiled C code. Explicitly document the boundary edge behavior (e.g., lower bound inclusive, upper bound exclusive) to guarantee deterministic tag assignment when atoms lie exactly on the specified planes.
3.  **Atomic Tagging Logic:** Implement precise Python logic explicitly mapping the mathematically generated boolean masking arrays accurately into positive integer values assigned securely directly to the `ase.Atoms.set_tags()` property efficiently safely cleanly completely. 4.  **Integrate Compiler Mapping:** Update strictly the existing `compiler.py` specifically to accurately utilize the explicit spatial module seamlessly securely mapping spatial explicit objects into correct LAMMPS explicitly string-based valid commands completely safely successfully precisely cleanly. 6.  **Type Verification and Error Handling:** Implement strict type hinting across the entire `spatial.py` module, specifically utilizing Python 3.11 features to note the expected shapes of the Numpy arrays (e.g., `NDArray[np.float64]` for positions matrices and `NDArray[np.bool_]` for intersection masks) to leverage advanced static analysis tools like Mypy. 7.  **Propagate Tags to Evaluator:** Ensure the integer tags generated by the spatial module are properly propagated to the `TwoTierEvaluatorConfig` within the compiler. The compiler must automatically configure the active learning evaluator to explicitly ignore MACE uncertainty variance scores for any atoms assigned the `ACTION_FREEZE` tag. This logic optimizes the active learning loop's computational speed by instructing the GPU to completely skip variance evaluation for geometry that is physically constrained from moving, saving significant execution time over millions of MD steps.
