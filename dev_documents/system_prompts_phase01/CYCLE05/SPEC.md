# Cycle 05: Accuracy vs Speed Orchestration Engine

## Summary
The primary objective of Cycle 05 focuses on establishing the highly robust mathematical translation layer bridging the gap between the single 1-10 visual slider and the complex active learning thresholds. This specifically requires the development of the `pyacemaker.domain_models.heuristics` module and its strict flawless integration with the existing robust `pyacemaker.domain_models.compiler` logic.

By completing Cycle 05, the system mathematically enables non-expert engineers to dynamically set the highly complex real-time physical simulation trajectory natively without understanding the underlying physics parameters. The "Accuracy vs. Speed" slider is the philosophical cornerstone of the Intent-Driven GUI. It abstracts away dozens of interconnected, highly sensitive parameters (such as the MACE uncertainty threshold, the learning rate for the Pacemaker, the frequency of DFT calls, and the aggressiveness of the molecular dynamics timestep) into a single, intuitive control. This cycle involves the complex, non-linear mapping required to ensure that a setting of '1' produces a fast, exploratory calculation (sacrificing precision), while a setting of '10' mandates extremely rigorous, slow, and highly accurate quantum mechanical verifications at every step.

This heuristic mapping is not simply a linear interpolation. It must respect the fundamental physical boundaries of the simulation. For example, setting the threshold for DFT calls too low might result in continuous, unnecessary oracle invocations (a "runaway" active learning state), while setting it too high risks the simulation exploring wildly unphysical territories before the MLIP can correct it. The heuristic engine must employ expertly crafted, non-linear scaling functions (e.g., exponential decay or logarithmic growth) to map the simple integer input to safe, stable, and scientifically sound threshold values.

The implementation of this cycle represents a fundamental shift in how materials simulation software is designed. Instead of exposing a massive configuration file with hundreds of esoteric flags, the GUI exposes a single "Intent". The backend `heuristics` module acts as a virtual expert system, translating that intent into the precise numerical values required by LAMMPS, Quantum ESPRESSO, and the MACE active learning loop. This effectively democratizes advanced molecular dynamics, making it accessible to experimentalists and engineers who may not possess deep theoretical knowledge of density functional theory convergence criteria or molecular dynamics integration algorithms. By successfully completing Cycle 05, PyAceMaker transitions from a tool strictly for computational chemists into a platform for general materials design.

## System Architecture
The implementation aligns with the complete architecture mapping mathematical trajectory parameters. We introduce `pyacemaker.domain_models.heuristics`. The `pyacemaker.domain_models.heuristics` acts as the purely functional mathematical mapping, converting the abstract slider objects precisely into mathematically correct `WorkflowConfig` parameters.

```text
src/pyacemaker/
├── api/                       # [EXISTING]
├── domain_models/
│   ├── compiler.py            # [MODIFIED] Heuristics invocation
│   └── heuristics.py          # [NEW] Highly accurate mathematical bounds
└── ...
```

The architecture strictly ensures that all heuristic mathematics operate locally and securely on safe `WorkflowConfig` fields exclusively in memory before the semantic compilation finishes. The module will act as a dependency for the `compiler.py`. When the compiler encounters an `IntentRequest` containing an `accuracy_speed_slider` value, it will pass this integer to the `heuristics.py` functions. These functions will return a fully populated, highly optimized dictionary of hyperparameters. The compiler will then merge these intelligent defaults into the final `WorkflowConfig` object. This architecture isolates the complex scaling logic from the structural DAG mapping logic developed in Cycle 02.

The architectural boundary between the Semantic Compiler and the Heuristics Engine is critical for maintainability. The Semantic Compiler is responsible for the *topology* of the workflow (e.g., ensuring an active learning loop follows an initial structure). The Heuristics Engine is entirely responsible for the *physics* of the workflow (e.g., determining the integration timestep). By decoupling these concerns, we ensure that if a new, more efficient active learning algorithm is introduced in the future—perhaps one that requires entirely different hyperparameter names or scaling laws—we only need to update the `heuristics.py` module. The React frontend and the Semantic Compiler's DAG parsing logic remain completely untouched. This is the essence of a clean, service-oriented architecture applied to scientific computing.

Furthermore, the architecture must support manual overrides. The Intent-Driven GUI will eventually feature an "Advanced Mode" toggle, allowing expert users to explicitly define specific parameters (like a custom `ecutwfc` for Quantum ESPRESSO or a specific learning rate scheduler for the Pacemaker MLIP trainer) while still relying on the slider for the rest of the configuration. The architecture must implement a strict priority merging strategy to resolve conflicts between heuristic defaults and user overrides. The required hierarchy is:

1.  **Hardcoded physical limits:** The system must never violate fundamental physical constraints (e.g., negative temperatures are forbidden, timestep cannot exceed 3.0 fs).
2.  **Explicit user overrides:** Values provided by the user in the "Advanced Settings" panel of the React GUI always override everything below this level.
3.  **Heuristically generated defaults:** The sophisticated, non-linear values generated by `heuristics.py` based on the 1-10 slider.
4.  **Base PyAceMaker engine defaults:** The fallback values defined in the Pydantic models (e.g., `Field(default=...)`) if a parameter is entirely unmentioned by both the user and the heuristic engine.

This tiered resolution strategy guarantees that the system is safe by default, flexible for experts, and completely abstract for beginners. The `compiler.py` will orchestrate this merging process. It will invoke the heuristics engine to generate tier 3, then deeply merge the user's manual JSON overrides (tier 2) on top of it, and finally pass the combined dictionary to the `WorkflowConfig` constructor, which naturally handles tier 4 and validates against tier 1. This ensures the resulting configuration is always valid and reflects the exact intent of the user, whether that intent is simple or highly detailed.

The architecture of the `heuristics.py` module itself must be highly modular. It should not consist of a single, massive function containing dozens of `if...elif` blocks mapping integers to dictionaries. Instead, it must utilize a suite of independent, mathematically rigorous scaling functions (e.g., `_scale_dft_threshold(slider: int) -> float`, `_scale_md_timestep(slider: int) -> float`). This functional decomposition allows each heuristic parameter to be unit-tested in isolation, ensuring the mathematical curves behave predictably across the entire domain from 1 to 10. It also allows developers to easily tweak individual parameters (e.g., making the learning rate decay more aggressively) without accidentally breaking the scaling logic of unrelated parameters like the barostat damping constant.

## Design Architecture
The `pyacemaker.domain_models.heuristics` houses the purely mathematical interpolation algorithms cleanly. This layer effectively transforms correctly ordered integers (e.g., 1-10) into strictly bounded numerical float parameters, precisely configuring the Two-Tier Evaluator cleanly.

A key domain invariant dictates strictly that the resulting heuristic parameters safely assigned to the `WorkflowConfig` must mathematically contain valid positive floats. The mapping algorithm translates these integer values precisely into matching configuration objects seamlessly safely. For example, a slider value of `8` (Accuracy priority) might map to a `candidate_threshold` of 0.05 eV/atom, while a value of `2` (Speed priority) might map to 0.2 eV/atom. These exact values must be meticulously calibrated.

The design of the heuristic engine must be deterministic and transparent. The scaling functions (e.g., `calculate_threshold(slider_value)`) should ideally be based on published benchmarking data or established rules of thumb within the materials informatics community. The module will utilize Numpy's mathematical functions to guarantee precision and performance, even though the calculations are simple scalars, to maintain consistency with the rest of the scientific stack. The design also dictates that the heuristics must be extensible; if a new active learning algorithm is introduced in the future requiring entirely different parameters, the heuristic mappings can be updated without altering the simple 1-10 slider exposed to the React frontend.

The specific mathematical design of the scaling functions is crucial. A simple linear interpolation `y = mx + c` is often insufficient for physical parameters. For instance, the MACE uncertainty threshold (`candidate_threshold`) controls the exponential frequency of DFT calls. Therefore, the mapping from the 1-10 slider to this threshold must follow an inverse exponential or logarithmic curve. When the slider moves from 9 to 10 (Maximum Accuracy), the threshold should drop significantly more steeply than when it moves from 1 to 2. This ensures that the extreme ends of the slider provide meaningful, noticeable differences in simulation behavior, effectively giving the user "fine control" at the critical accuracy boundary and "coarse control" at the exploratory speed boundary.

Similarly, discrete integer parameters like `check_interval` (how many MD steps occur between uncertainty evaluations) must be calculated using step functions or ceiling/floor algorithms. If the user prioritizes "Speed" (slider = 1), the system might only evaluate uncertainty every 10 or 20 MD steps, massively accelerating the simulation at the risk of missing rare events or over-extrapolating. If the user prioritizes "Accuracy" (slider = 10), the system must evaluate uncertainty every single MD step, creating a bottleneck but guaranteeing absolute fidelity. The `heuristics.py` module encapsulates these complex, non-linear relationships, presenting a clean, strongly typed dictionary interface to the rest of the application.

The data structures exchanged between the `compiler.py` and `heuristics.py` must be explicitly defined using Python's `typing.TypedDict` or, preferably, internal Pydantic sub-models. This ensures that the keys generated by the heuristic engine (e.g., `threshold_call_dft`, `integration_timestep`, `max_training_epochs`) exactly match the expected fields within the `WorkflowConfig` hierarchy. This prevents subtle `KeyError` exceptions or silent misconfigurations during the merging process. If a developer accidentally misspells `candidate_threshold` as `candidate_treshold` inside the heuristic equations, the type checker (Mypy) must immediately flag this error during continuous integration, long before the code is deployed or a user attempts a compilation. This strict typing is essential for managing the complexity of generating configurations containing potentially hundreds of distinct physical parameters.

## Implementation Approach
The implementation of the heuristic engine requires careful tuning of mathematical functions and rigorous validation against known safe physical configurations. We will construct this module using a highly parameterized, function-driven approach to ensure testability and maintainability across the entire spectrum of the user-facing slider.

1.  **Establish Heuristics Module:** Create the `heuristics.py` module inside the `src/pyacemaker/domain_models/` directory. Define a suite of pure mathematical scalar algorithms operating seamlessly upon the incoming integer slider input (ranging from 1 to 10) effectively, correctly, and cleanly perfectly. This module must expose a single, central mapping function, `get_heuristics_for_slider(value: int, element_context: list[str]) -> HeuristicConfigDict`. We must define a robust `TypedDict` or internal Pydantic schema specifically named `HeuristicConfigDict` to strictly type the return dictionary of this function, ensuring absolute key alignment with the massive nested hierarchy of the final `WorkflowConfig` model.
2.  **Define Non-Linear Scaling Functions:** Implement precise logic mapping the provided integer slider (1-10) to highly specific physical parameters using heavily calibrated non-linear equations. For example, the `candidate_threshold` scalar (which dictates when MACE pauses to request a Quantum ESPRESSO DFT evaluation) must scale exponentially to ensure that high-accuracy settings become exquisitely sensitive to even minuscule atomic uncertainties. Use `numpy.exp()` or `numpy.log10()` explicitly to construct these complex tuning curves. Calibrate the mathematical base and exponent values so that a neutral slider value of `5` precisely generates the standard, widely accepted MLIP community defaults (e.g., exactly `0.1 eV/atom` threshold, exactly `1.0 fs` integration timestep, exactly `40.0 Ry` kinetic energy cutoff).
3.  **Enhance Compiler Priority Merging:** Update precisely the `compiler.py` module to correctly consume these new heuristics. Specifically define the critical dictionary injection mechanism where the `SemanticCompiler` actively calls the `heuristics` module and safely merges the returned multi-layered dictionary deep into the `TwoTierEvaluatorConfig`, `LammpsDriverConfig`, and `TrainerConfig` Pydantic models. Implement the strict 4-tier priority merging logic definitively described in the system architecture. Utilize deep dictionary merging utilities (e.g., custom recursive update functions or `pydantic.model_copy(update=...)`) to strictly ensure nested configuration blocks (like the deep Quantum ESPRESSO `system_settings` kwargs) are correctly overridden by manual user inputs without accidentally obliterating unmentioned, heuristically generated keys residing at the same nested depth.
4.  **Enforce Safe Mathematical Bounds:** Implement strict bounds clamping checks directly within the fundamental heuristics functions. Even if the mathematical exponential scaling equation produces a theoretically valid but practically unsafe value, the function must aggressively clamp the final output between a physically defined minimum and maximum constant to prevent catastrophic simulation failure. For instance, mathematically ensure a Pacemaker model learning rate never exceeds `0.1` (causing exploding gradients) or drops below `1e-6` (causing stalled training) regardless of the slider value. Similarly, use built-in Python `min()` and `max()` functions to explicitly enforce that the LAMMPS MD timestep never wildly exceeds `3.0 fs` under any 'speed' configuration, preventing catastrophic energy drift during integration.
5.  **Refine Active Learning Intervals (Integer Clamping):** The single visual slider must also intelligently control discrete integer-based parameters, such as the exact frequency at which the active learning orchestrator evaluates the MACE uncertainty variance arrays (e.g., evaluating every `1` step for maximum Accuracy vs. every `20` steps for maximum Speed). Implement explicit mathematical rounding functions (specifically `math.floor` or `math.ceil` combined with strict `int()` casting) to guarantee these calculated intervals are perfectly valid integers before they are merged into the final Pydantic configuration payload. This strictly prevents the underlying LAMMPS C++ driver from crashing or throwing a segmentation fault when accidentally passed a floating-point number for a discrete simulation step count argument.
6.  **Implement Fallback Parameter Resolution:** Ensure the heuristics engine provides a truly complete, exhaustive set of default baseline parameters based on chemical context. If the system is analyzing a purely metallic slab (inferred from the `INITIAL_STRUCTURE` node passing a `["Pt"]` element context), the heuristics engine should intelligently default to Marzari-Vanderbilt smearing (`smearing = 'mv'`) and a broadening parameter of `degauss = 0.02` for the Quantum ESPRESSO SCF cycle. The heuristics engine must contain enough embedded domain knowledge to generate these sane defaults autonomously based on the minimal context provided by the `IntentRequest`, relying on hardcoded chemical lookup tables for common periodic table elements and standardized simulation types to ensure a "zero-config" experience successfully yields physically meaningful results.

## Test Strategy
The testing isolates the purely mathematical functional translation successfully. The strategy focuses on verifying that the scaling equations behave correctly across the entire 1-10 domain and that the edge cases do not violate physical constraints, ensuring the compiler acts as a mathematically rigorous translator of intent.

**Unit Testing Approach:**
Extensively and rigorously test the newly independent `heuristics.py` module strictly inside the `tests/unit/test_heuristics.py` suite. We will parameterize a test fixture to continuously inject integer values from exactly `1` up to `10` into the core function and rigorously specifically assert that the returned nested float parameters perfectly match manually pre-calculated expected mathematical boundaries cleanly. We will write comprehensive parameterized tests verifying that for absolutely every single integer input within the valid domain, the resulting `candidate_threshold` value is strictly greater than `0.0`, and that the calculated relationship is strictly monotonically decreasing (e.g., as the slider moves incrementally from 1 to 10, the threshold float must consistently become smaller, tightening the precision requirements without exception).

We will explicitly and aggressively test the bounds clamping logic using edge case values. For example, if the defined scaling equation theoretically calculates a massive integration timestep of `4.5 fs` for a slider value of `1` (extreme speed), the unit test must explicitly assert that the heuristic engine correctly intercepted this value and clamped it firmly back to the mathematically defined safe maximum constant of exactly `3.0 fs`. We will also heavily test out-of-bounds GUI inputs (like an integer `0`, integer `11`, or unexpected floating-point numbers like `5.5` sent via a bypassed frontend) to verify that the module correctly and immediately raises a `ValueError` exception, completely ensuring the FastAPI routing layer's Pydantic validation is robustly backed up by domain-level defensive programming inside the mathematical translation layer itself. The unit tests will meticulously loop over the entire valid 1-10 integer range and exhaustively assert that absolutely no generated key-value pair produces a `NaN` (Not a Number) or `Infinity` float representation, which would instantly crash the underlying C++ physics engines upon initialization.

**Integration Testing Approach:**
Within the `tests/integration/test_compiler.py` test suite, update the API tests thoroughly testing that the full visual workflow mathematically generates safely explicit, highly complex, deeply valid JSON configurations correctly under varying intents. We will utilize the test client to submit two entirely separate `IntentRequest` JSON payloads directly to the compiler endpoint: one payload with the visual slider set exactly to `1` (Speed), and another payload with the slider set exactly to `10` (Accuracy). The integration test will then recursively inspect the returned `WorkflowConfig` Python objects and explicitly assert that the heavily nested `config.active_learning.evaluator.threshold_call_dft` float parameter is significantly lower in the Accuracy payload compared precisely to the Speed payload. It will concurrently assert that the `config.lammps_driver.integration_timestep` is correspondingly much larger in the Speed payload, proving the single slider successfully modulated multiple distinct physical sub-engines simultaneously.

Furthermore, we will explicitly test the complex priority merging logic governing "Advanced Mode" overrides. We will submit an Intent payload with the accuracy slider set to `5`, but we will explicitly include a manual JSON override block setting `ecutwfc: 80.0` within the `advanced_settings` node data. This definitively proves that the semantic compiler system correctly accommodates expert users by preserving manual overrides while seamlessly maintaining the abstract heuristic interface for beginners across all other unmentioned parameters. Finally, we will submit a malicious payload with a manual override that intentionally violates an absolute safety physical bound (e.g., setting `integration_timestep: -1.0` fs). The test will rigorously verify that the system correctly catches this tier-1 violation via Pydantic model validation and successfully returns an HTTP 422 Unprocessable Entity error directly to the simulated client, guaranteeing the entire Intent-Driven pipeline functions correctly, securely, and safely from the initial API boundary request all the way down to the final instantiation of the physical simulation parameters.
