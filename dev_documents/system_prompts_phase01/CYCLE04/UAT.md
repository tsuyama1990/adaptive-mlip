# Cycle 04: Real-time Telemetry and WebSockets - UAT

## Test Scenarios
The primary user acceptance testing scenarios focus specifically on proving the absolute robustness and flawless mathematical translation of the visual bounding-box representations generated by the React Flow/Three.js frontend and their precise integration seamlessly into the highly specific, text-based atomic telemetry mechanisms native to WebSockets. The UAT simulates the safe mathematical processing of a simplified spatial GUI representation perfectly. This cycle proves that the user can actually "see" what the AI is doing in real-time, removing the "black box" nature of active learning.

* **SCENARIO-04-A [Priority: High] - Successful Real-time Trajectory Streaming:** The UAT must simulate a user completing the simplified spatial configuration. The interface successfully receives a fully valid mathematical precise JSON spatial bounding box payload directly (e.g., Z-min: 0.0, Z-max: 5.0, Action: "FREEZE") into the React application. The API explicitly correctly streams the entire spatial configuration accurately into the highly precise nested schema natively required. This demonstrates the core value of live visual feedback. The simulated user starts an active learning workflow for a complex metallic surface model. The frontend establishes a WebSocket connection to the `/api/v1/telemetry/stream` endpoint. As the backend LAMMPS engine begins the molecular dynamics simulation, it publishes trajectory frames at a rate of 100 frames per second. The telemetry module downsamples this stream to a manageable 10 frames per second for visualization. The frontend successfully receives these downsampled frames as JSON payloads containing the updated Cartesian coordinates of all 5,000 atoms in the system. The test verifies that these frames arrive sequentially, without significant latency, data corruption, or overwhelming the client's memory, allowing the Three.js viewer to smoothly animate the physical vibrations and movements of the atoms in real-time. This confirms the asynchronous Pub/Sub architecture correctly decoupled the heavy physics calculations from the network transmission, preventing the simulation from bottlenecking the UI and vice versa. Furthermore, the test will verify that the initial `SystemTopology` frame correctly transmits the atomic numbers and bounding box limits once upon connection, proving that the telemetry schema avoids redundant data transmission and efficiently utilizes available network bandwidth.

* **SCENARIO-04-B [Priority: High] - Accurate Mathematical Uncertainty Heatmap Visualization:** The UAT tests that complex internal vector mathematical logic correctly populates the correct intelligent Boolean masking arrays. When the Two-Tier Evaluator flags an atom due to high MACE uncertainty, the WebSocket must instantly broadcast this specific atomic index and its corresponding uncertainty score. In this scenario, the simulation encounters a novel, unseen atomic configuration (e.g., a surface adatom moving to a high-energy transition state, or a molecule dissociating). The underlying MACE oracle calculates a high variance for these specific atoms. The PyAceMaker orchestrator detects that this variance exceeds the heuristically defined `candidate_threshold` and halts the MD run to invoke Quantum ESPRESSO. Crucially, the orchestrator publishes this specific "high uncertainty event frame" to the telemetry queue, bypassing all downsampling logic. The WebSocket endpoint immediately streams a specialized JSON payload to the frontend. This payload contains the specific atomic indices that triggered the halt and their exact variance values (e.g., `variances: [0.01, 0.02, 0.85, 0.01...]` where index 2 represents the highly uncertain adatom). The test simulates the frontend receiving this data and verifies it contains the necessary information to render a visual "heatmap" over the 3D structure, coloring the highly uncertain adatom bright red while keeping the bulk crystal transparent. This proves the system successfully communicates the AI's internal decision-making process to the human operator, providing crucial transparency and trust in the active learning loop. The test suite will also assert that during deterministic phases (e.g., when the simulation is running purely classical MD without evaluating uncertainty), the `variances` array is omitted from the JSON payload or set to null, proving the telemetry module intelligently optimizes the payload structure dynamically based on the orchestrator's internal state machine.

* **SCENARIO-04-C [Priority: Medium] - Robustness to Network Disconnects and Backpressure:** The UAT will simulate a scenario where the simulated frontend unexpectedly drops the WebSocket connection while the backend is actively streaming a high-frequency trajectory. The system must recognize the disconnect, clean up the subscriber session, and continue running the underlying orchestrator calculation without raising fatal exceptions or crashing. The simulated user initiates a very fast molecular dynamics run generating hundreds of frames per second. The frontend establishes a connection and begins receiving data normally. Suddenly, the user abruptly closes the browser tab, severing the WebSocket connection ungracefully (i.e., without sending a standard close frame). The backend broadcasting task must catch the resulting `WebSocketDisconnect` exception instantly. It must deregister that specific client connection from its active subscriber list. Most importantly, the test must verify that the core PyAceMaker orchestrator and the LAMMPS simulation continue to run uninterrupted in the background, proving that the web interface cannot fatally crash the physics engine. Furthermore, the test will simulate a slow network connection where the frontend cannot consume frames as fast as they are produced by LAMMPS. It will verify that the backend telemetry queue implements a strict "drop-oldest" policy, successfully discarding stale trajectory frames when the internal queue reaches its maximum size limit (e.g., 100 frames), preventing the FastAPI server from consuming unbounded memory and crashing with an Out-Of-Memory error. Finally, the test will simulate multiple clients connecting to the same workflow stream simultaneously, asserting that the backend Pub/Sub architecture correctly broadcasts the identical frame to all clients concurrently without duplicating the serialization workload, demonstrating true scalability.

## Behavior Definitions
These behavior definitions map to the exact User Test Scenarios, specifically defining the deterministic Gherkin-style assertions expected from the PyAceMaker Telemetry module. This provides concrete, verifiable rules for the streaming architecture and ensures the real-time visualization is a faithful representation of the underlying simulation state.

**Feature: Real-Time Atomic Trajectory Streaming and UI Synchronization**

**Scenario 1: Flawless Translation of Trajectory Frames to WebSocket Payload**
**GIVEN** the PyAceMaker Orchestrator is actively running a molecular dynamics simulation
**AND** the frontend UI has established a healthy WebSocket connection to `/api/v1/telemetry/stream`
**WHEN** the LAMMPS engine completes a predefined number of integration steps and publishes a new `ase.Atoms` frame
**THEN** the backend telemetry module successfully pops this frame from the thread-safe `IoManager` queue
**AND** serializes the atomic positions, chemical symbols, and cell parameters into a compact `TelemetryFrame` JSON structure, explicitly converting numpy arrays to standard python lists
**AND** transmits this JSON payload over the WebSocket connection to the connected frontend client
**AND** the frontend successfully parses this payload, allowing the 3D viewer to update the atomic coordinates synchronously with the simulation without perceptible latency.

**Scenario 2: Transmission of High-Uncertainty Events (Active Learning Trigger)**
**GIVEN** the PyAceMaker active learning orchestrator is running and streaming standard, downsampled trajectory data
**AND** the `TwoTierEvaluator` identifies a specific atomic configuration where the MACE variance exceeds the user's defined `candidate_threshold`
**WHEN** the orchestrator halts the MD simulation to extract an intelligent cutout and initiates the Quantum ESPRESSO validation phase
**THEN** it immediately publishes a specialized, non-downsampled "high uncertainty" event frame to the telemetry queue
**AND** the active WebSocket connection immediately receives a distinct JSON payload detailing this state transition to `RUNNING_DFT`
**AND** the payload includes an array mapping the specific atomic indices to their calculated variance scores, providing the exact data required for the frontend to render the uncertainty heatmap correctly and highlight the exact atoms causing the active learning trigger.

**Scenario 3: Resilient Handling of Client Disconnections and Queue Backpressure**
**GIVEN** a frontend client is actively receiving a high-frequency stream of `TelemetryFrame` payloads from a fast simulation
**WHEN** the client abruptly terminates the WebSocket connection without sending a proper close frame (e.g., closing the browser tab or experiencing a network timeout)
**THEN** the FastAPI broadcasting task immediately catches the resulting `WebSocketDisconnect` exception
**AND** removes the dead connection object from the global active subscriber set, ensuring no further messages are sent to that socket
**AND** the underlying PyAceMaker active learning simulation continues executing its complex physics routines unaffected by the frontend network failure, preventing data loss or process crashes.
**WHEN** the LAMMPS simulation generates frames faster than the network can transmit them
**THEN** the internal `asyncio.Queue` reaches its configured `maxsize`
**AND** the publisher implements a drop-oldest policy, successfully pushing new frames onto the queue while discarding the oldest un-transmitted frames, ensuring the server's memory footprint remains stable and the UI never falls infinitely behind the simulation's current state.
