# Cycle 04: Real-time Telemetry and WebSockets

## Summary
The primary objective of Cycle 04 focuses on establishing the highly robust, asynchronous real-time telemetry streaming layer bridging the gap between the active learning orchestrator and the Three.js frontend. This specifically requires the development of the `pyacemaker.api.routes.telemetry` module and its strict flawless integration with the existing robust `pyacemaker.logger` and `IoManager` logic.

By completing Cycle 04, the system mathematically enables non-expert engineers to dynamically view the complex metallic surface real-time physical simulation trajectory natively. This visual feedback is paramount for building trust in the underlying AI models. Rather than staring at a static terminal output or parsing gigabytes of log files, the user can visually monitor the atomic interactions as they occur, specifically observing regions where the MACE oracle flags high uncertainty. This immediate visual confirmation transforms a black-box machine learning process into a transparent, understandable physical simulation.

The integration relies heavily on asynchronous programming paradigms, specifically utilizing Python's `asyncio` framework and the FastAPI WebSocket implementation. This ensures that the computationally heavy molecular dynamics loops running in the background are never blocked or throttled by the process of broadcasting data to connected web clients. The architecture mandates a decoupled Publisher-Subscriber (Pub/Sub) pattern, where the orchestrator blindly publishes state changes and the WebSocket handlers subscribe to these events, streaming them to the React frontend efficiently.

This cycle fundamentally changes how users interact with long-running PyAceMaker jobs. Instead of submitting a configuration and waiting days for a static result, the Intent-Driven GUI becomes a dynamic dashboard. The real-time telemetry allows users to detect unphysical behavior early—for example, if a surface reconstruction goes wrong or a molecule evaporates unexpectedly due to a bad thermostat parameter—and manually intervene or abort the simulation, saving significant computational budget. The telemetry layer must handle high-throughput, potentially bursts of thousands of trajectory frames per minute, without overwhelming the client's browser or causing memory leaks on the server. This requires careful consideration of data serialization, downsampling strategies, and robust connection lifecycle management. The ability to visualize the *uncertainty* of the AI in real-time, rendered directly onto the atoms, is the defining feature that separates PyAceMaker from traditional MD visualizers like OVITO.

## System Architecture
The implementation aligns with the complete architecture mapping mathematical trajectory parameters. We introduce `pyacemaker.api.routes.telemetry`. The `pyacemaker.logger` module acts as the functional mathematical pub/sub, converting the abstract `logging` objects precisely into mathematically correct `WebSocket` streams.

```text
src/pyacemaker/
├── api/                       # [EXISTING]
│   ├── routes/                # [EXISTING]
│   │   ├── ...
│   │   └── telemetry.py       # [NEW] Highly accurate WebSocket streaming endpoints
├── domain_models/
│   ├── ...
├── logger.py                  # [MODIFIED] Pub/Sub mechanisms for real-time state
└── ...
```

The architecture strictly ensures that all spatial mathematics operate locally and securely on safe `logging` structures exclusively in memory before committing to string-based WebSocket outputs. The `IoManager`, previously responsible only for disk I/O (e.g., writing XYZ trajectories), will be augmented to push relevant frames onto an internal `asyncio.Queue`. The FastAPI WebSocket endpoints will act as consumers of this queue, serializing the atomic positions, forces, and critically, the localized uncertainty metrics calculated by the Two-Tier Evaluator, into lightweight JSON payloads suitable for high-frequency transmission.

The architectural design of the telemetry subsystem relies on a strict separation between the data producers and the data consumers. The PyAceMaker core orchestrator, LAMMPS driver, and MACE oracle are the producers. They operate in a synchronous, computationally intense environment, often utilizing `concurrent.futures.ProcessPoolExecutor` to manage heavy calculations. They must not be burdened with managing network connections or formatting JSON strings. Therefore, we introduce a singleton instance of an asynchronous event broker within the `pyacemaker.logger` module. When a producer generates a new trajectory frame or triggers a significant state transition (e.g., "DFT Validation Started", "MACE Training Completed", "Intelligent Cutout Extracted"), it simply calls a synchronous `publish()` method on the logger.

This `publish()` method acts as a vital bridge across the synchronous/asynchronous boundary. It takes the complex Python objects (like an `ase.Atoms` instance with associated variance arrays attached to the `info` dictionary) and places them into a thread-safe, non-blocking queue (e.g., using `asyncio.run_coroutine_threadsafe` to inject the message from a worker thread into the main FastAPI event loop). The architecture then employs a dedicated asynchronous worker task, managed by the FastAPI application lifecycle (`@app.on_event("startup")`), to continuously monitor this queue. When data arrives, the worker serializes it into the highly optimized JSON schema required by the frontend and broadcasts it concurrently to all currently active WebSocket connections maintained by the `telemetry.py` router.

This Pub/Sub architecture is critical for several fundamental reasons regarding system stability. First, it ensures that if no React clients are connected to the GUI, the active learning simulation continues to run at maximum possible speed without attempting to serialize data or send it to nowhere; the queue publisher simply acts as a no-op if the subscriber count is zero. Second, it allows multiple frontend clients to connect simultaneously and view the exact same simulation instance in real-time without multiplying the serialization overhead. The centralized worker task serializes the frame exactly once and sends the identical string to all open sockets. Finally, this decoupling provides a natural mechanism for handling network backpressure. If the frontend browser cannot consume frames as fast as LAMMPS produces them (which is highly likely during pure MLIP dynamics where thousands of steps execute per second), the queue can implement a strict "drop-oldest" policy. This ensures that the visualizer always displays the most recent state rather than building up an infinite backlog of stale frames that would eventually crash the server with an Out-Of-Memory (OOM) error or introduce massive rendering lag on the client side.

The WebSocket routing module itself (`telemetry.py`) is deliberately designed to be as lightweight as possible. Its primary responsibilities are handling the initial HTTP upgrade request, managing the connection handshake, maintaining the registry of active client connections (e.g., adding them to a global `set`), and managing the lifecycle of the socket. Crucially, it must catch `WebSocketDisconnect` exceptions when a user closes their browser tab or experiences a network dropout, gracefully removing the specific client from the active subscriber list to prevent the broadcasting loop from raising unhandled exceptions. It does not perform any data manipulation or physics calculations. This strict architectural boundary guarantees that the real-time streaming capabilities enhance the user experience without compromising the stability or performance of the core scientific engine. The architecture also dictates that the telemetry stream is strictly one-way (server to client) for trajectory data; the client cannot control the simulation via this socket, ensuring the simulation state machine remains secure and deterministic.

## Design Architecture
The `pyacemaker.api.routes.telemetry` houses the purely mathematical pub/sub algorithms cleanly. This layer mathematically transforms strictly mathematical ordered boundaries explicitly (e.g., atomic coordinates, force vectors) into serialized JSON strings, filtering `WebSocket` payloads perfectly cleanly.

A key domain invariant dictates strictly that the `websocket` property safely on the `api` instance must mathematically contain strictly valid positive JSON. The mapping algorithm translates these data structures precisely into matching React flow seamlessly safely. The JSON schema for the telemetry payload must be strictly defined to minimize bandwidth overhead. It will prioritize transferring incremental changes (deltas) where possible, or downsampling the trajectory frames if the simulation timestep is extremely fine. The design completely prohibits sending serialized Python objects (like `pickle` payloads) over the socket due to massive security risks.

The pub/sub implementation within `pyacemaker.logger` must guarantee thread safety above all else. Because the LAMMPS engine and the MACE oracle operate in separate processes or threads managed by the `ProcessPoolExecutor`, the telemetry queue must be capable of receiving messages concurrently from multiple producers without data corruption, race conditions, or deadlocks. This is achieved by employing robust concurrency primitives provided by the Python standard library, isolating the complex physics calculations from the relatively simple task of data broadcasting.

The data design for the telemetry payload centers around two new strict Pydantic models: `SystemTopology` and `TelemetryFrame`. These models must be meticulously optimized for network transmission. Sending full string representations of chemical symbols for every atom in every frame (e.g., `["Pt", "Pt", "Pt"...]`) is incredibly inefficient and consumes unnecessary bandwidth. The design dictates a stateful transmission protocol. The initial connection handshake must send the "System Topology" payload containing static information: the array of atomic numbers, the total number of atoms, fixed spatial boundaries, and the static cell dimensions (if running NVT/NVE).

Subsequent `TelemetryFrame` payloads broadcast during the active learning loop will contain only dynamic data: flattened Numpy arrays of Cartesian coordinates (`positions`), force vectors (`forces`), and critically, the atomic uncertainty metrics (`variances`) calculated by the `TwoTierEvaluator`. The `TelemetryFrame` model will enforce strict typing on these arrays, ensuring they are serialized as compact, 1D lists of floats rather than nested arrays. A critical design decision is the inclusion of the `step_number` and the `current_state` enumeration (e.g., `RUNNING_MD`, `EVALUATING_UNCERTAINTY`, `RUNNING_DFT`, `EXTRACTING_CUTOUT`) in every frame. This allows the React frontend to perfectly synchronize its 3D rendering with the internal state machine of the orchestrator, updating UI components like progress bars, status indicators, and current simulation time precisely in step with the physics simulation.

To address the severe performance gap between molecular dynamics (which can run thousands of steps per second) and web rendering (which typically runs at 60 frames per second), the `logger` module's design incorporates an intelligent downsampling heuristic. The `IoManager` will not push every single computed frame to the telemetry queue. Instead, it will implement a configurable `stream_interval` (e.g., publishing only every 100th frame). However, the design invariant strictly requires that *all* critical active learning events—such as the exact frame that triggered a DFT calculation due to high uncertainty, or the exact structure of an extracted cutout—must bypass this downsampling filter. These critical events are guaranteed delivery to the frontend. This ensures the user never misses the exact moment an extrapolation event occurs, which is the primary value proposition of the visual monitoring system, allowing them to inspect the exact atomic configuration that confused the MLIP.

## Implementation Approach
The implementation of the real-time telemetry subsystem requires careful handling of asynchronous event loops, multi-threading synchronization, and efficient data serialization to ensure data flows smoothly from the backend to the frontend without causing the Python Global Interpreter Lock (GIL) to stall the physics calculations. This requires bridging the asynchronous world of FastAPI WebSockets with the largely synchronous, CPU-bound world of PyAceMaker's core execution engines.

1.  **Enhance Logger and IoManager:** Update precisely the `logger.py` and `core/io_manager.py` modules. Specifically define a thread-safe mechanism within the core application state. Instead of relying purely on a synchronous `queue.Queue`, we will utilize an `asyncio.Queue` that is bridged securely. When a producer thread (like the LAMMPS execution loop) generates a frame, it will use `asyncio.run_coroutine_threadsafe(queue.put(frame), loop)` to safely inject the message directly into the main FastAPI `asyncio` event loop. Modify the `IoManager.write_trajectory` method to not only append to the `.xyz` file on disk but also construct a minimal `TelemetryFrame` dictionary and aggressively place it onto this queue. Apply a `stream_interval` downsampling logic based directly on the current MD timestep. Ensure the internal queue is instantiated with a strict `maxsize` (e.g., `maxsize=100`) to strictly enforce backpressure across the entire system.
2.  **Define Telemetry Schemas (JSON Optimization):** Create the completely new `TelemetryFrame` and `SystemTopology` Pydantic models within a new dedicated schema file (e.g., `domain_models/telemetry_schema.py`) or within the existing `gui_schema.py`. Utilize `pydantic.Field` heavily to enforce strict formatting rules. Crucially, ensure that multi-dimensional Numpy arrays (like the 3xN `positions` matrix) are correctly flattened and explicitly converted to standard Python lists of floats before serialization. Use custom Pydantic `@model_serializer` methods on these models to guarantee optimal JSON encoding speed, utilizing fast libraries like `orjson` if available. The schema must explicitly include optional fields for the `variances` array and a `current_state` enumeration (e.g., `RUNNING_MD`, `EVALUATING_UNCERTAINTY`).
3.  **Establish WebSocket Endpoint:** Create the entirely new `telemetry.py` module inside `api/routes/`. Define an asynchronous FastAPI WebSocket endpoint decorator (e.g., `@router.websocket("/stream/{workflow_id}")`). This endpoint function must immediately `await websocket.accept()` to initiate the upgrade protocol. It must then instantly add the resulting connection object to a globally managed set of active subscribers (e.g., a `ConnectionManager` singleton instance), and then enter an infinite `while True:` loop. This loop will silently `await websocket.receive_text()` to continuously monitor the connection state, allowing it to instantly detect when a client ungracefully drops the socket connection. Send the static `SystemTopology` payload immediately upon the initial successful handshake so the frontend Three.js viewer can initialize its geometry buffers.
4.  **Implement the Broadcasting Task:** Create a continuously running asynchronous background task (e.g., `asyncio.create_task(broadcast_loop())`) that executes indefinitely as long as the FastAPI server remains alive. This task should be initiated exclusively via FastAPI application lifespan events (`@app.on_event("startup")`). This task will continuously `await` items popping from the central telemetry queue. When an item is received, it iterates through the global set of active WebSocket subscribers and simultaneously calls `await connection.send_json(payload)`. Utilize `asyncio.gather(*tasks)` to broadcast the serialized JSON string to multiple connected frontend clients concurrently, maximizing throughput.
5.  **Handle Connection Lifecycles and Backpressure:** The WebSocket endpoint module must robustly handle sudden client disconnections (e.g., the user closing their browser tab or a network timeout occurring). Wrap the `send_json` broadcasting call in a specific `try...except WebSocketDisconnect:` block to catch the error and gracefully remove that specific client from the active subscriber list. To handle backpressure, implement a strict "drop-oldest" policy on the main telemetry queue. Do this by utilizing `queue.put_nowait(frame)` in the producer thread; if it hits an `asyncio.QueueFull` exception, the producer must immediately call `queue.get_nowait()` to pop and discard the oldest un-transmitted frame, and then retry the `put_nowait`. This absolutely prevents memory exhaustion if the LAMMPS C++ producers drastically outpace the web server's ability to transmit data over the network.
6.  **Integrate Orchestrator State Events:** Update the main `orchestrator.py` state machine heavily. The orchestrator must publish explicit status messages to the telemetry queue whenever it transitions between logical phases (e.g., generating a `{"type": "state_change", "new_state": "RUNNING_DFT"}` payload). This provides the React frontend with the necessary semantic context to update the UI beyond just blindly rendering atomic positions, allowing the user to precisely track the progress of long-running Quantum ESPRESSO DFT calculations or Pacemaker MLIP training epochs via visual progress bars.
7.  **Serialize Uncertainty Metrics:** Ensure absolutely that when the `TwoTierEvaluator` successfully calculates the variance array for an atomic configuration during an active learning check, this specific variance array is explicitly extracted and attached to the `TelemetryFrame` payload under the `variances` key. This is the crucial, defining data array required for the Three.js frontend to dynamically render the "uncertainty heatmap" directly onto the 3D atomic structure, providing the immediate visual feedback loop that lies at the core of the Intent-Driven design philosophy.

## Test Strategy
The testing isolates the purely mathematical functional translation successfully. The strategy focuses heavily on verifying the concurrency, thread safety, and reliability of the asynchronous queues without needing a real browser client. It must prove that the fast physics engine cannot overwhelm the slower web server. The tests must simulate extreme, multi-threaded load conditions to guarantee the architecture will survive in production environments handling complex molecular dynamics simulations.

**Unit Testing Approach:**
Extensively and rigorously test the newly enhanced `logger.py` and `IoManager` modules inside a dedicated `tests/unit/test_telemetry_pubsub.py` file. We will write explicit asynchronous unit tests using the `pytest-asyncio` library to thoroughly verify that messages pushed to the internal `asyncio.Queue` from multiple simulated concurrent producer threads (using `concurrent.futures.ThreadPoolExecutor` to perfectly mimic the asynchronous behavior of the LAMMPS and MACE engines) can be correctly and sequentially popped by a simulated asynchronous consumer task. We will assert this occurs without incorrectly raising `queue.Empty` exceptions prematurely or causing deadlocks in the Python event loop.

We will explicitly test the downsampling logic. We will write a test asserting that if the `stream_interval` is explicitly set to `10`, rapidly pushing exactly 100 sequential trajectory frames to the `IoManager` only results in exactly 10 resulting payloads entering the telemetry queue. We will heavily test the `TelemetryFrame` Pydantic model serialization, asserting that highly complex `ase.Atoms` objects containing large, multi-dimensional numpy coordinate arrays are correctly flattened into valid, highly compact JSON strings entirely without floating-point precision loss. We will verify that missing variance arrays are gracefully handled (e.g., correctly transmitting `null` or empty lists during purely deterministic classical MD phases).

Crucially, we will test the "drop-oldest" queue backpressure implementation. The test will forcefully fill the mock queue to its `maxsize` limit (e.g., 100 items). It will then assert that pushing new incoming messages successfully overwrites the oldest existing messages in the queue entirely without crashing the producer thread or raising unhandled `QueueFull` exceptions, proving the system is resilient to network bottlenecks.

**Integration Testing Approach:**
Within the `tests/integration/test_telemetry_endpoints.py` suite, we will thoroughly test that the full, precise workflow mathematically generates explicit JSON text string commands correctly and broadcasts them over the network. We will utilize the `httpx.AsyncClient` or the `fastapi.testclient.TestClient` equipped with built-in WebSocket support to establish a direct, simulated socket connection to the `/api/v1/telemetry/stream` endpoint.

The integration test will programmatically trigger events deep within a mocked PyAceMaker orchestrator. It will simulate the precise sequence of an active learning loop: the start of an MD run, the extremely rapid generation of several dozen standard trajectory frames, and a sudden, critical transition to a DFT validation state indicating high uncertainty. We will then explicitly assert that the exact corresponding sequence of JSON payloads (the initial `SystemTopology` handshake, the sequentially downsampled `TelemetryFrame` coordinates, and finally the `state_change` event) are received sequentially and perfectly intact over the WebSocket connection by the test client.

Furthermore, we will simulate a harsh client disconnect. The test will abruptly close the test WebSocket instance without sending a proper close frame, perfectly mimicking a user forcibly closing their browser window. We will assert that the backend FastAPI broadcasting task successfully catches the `WebSocketDisconnect` exception instantly, removes the dead client from the active registry, and continues processing the queue indefinitely completely without crashing the FastAPI ASGI server, hanging the orchestrator, or leaking memory over subsequent iterations. This rigorous end-to-end verification definitively proves the entire real-time pipeline, from simulation event generation down to raw network transmission, operates reliably under simulated, adversarial load conditions.
