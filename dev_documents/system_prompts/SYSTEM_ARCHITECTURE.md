# System Architecture for PyAceMaker

## 1. Summary
PyAceMaker is an advanced orchestration platform designed to automate the construction of robust Machine Learning Interatomic Potentials (MLIPs). The system orchestrates an Active Learning loop with a "Hierarchical Distillation" architecture to solve the critical challenges of long-timescale molecular dynamics simulations. By integrating a foundational MACE oracle alongside Quantum Espresso to filter uncertainty, the system seamlessly pauses MD without losing time-continuity, repairs extracted clusters by auto-passivating dangling bonds, filters thermal noise using a two-tier uncertainty system, and incrementally updates potentials to prevent catastrophic forgetting. The new requirements build upon the existing capabilities in a strictly additive manner, preserving the established core logic while radically expanding its robustness and scale.

## 2. System Design Objectives

The fundamental objective of the PyAceMaker Next-Generation architecture is to achieve scalable, highly reliable molecular dynamics (MD) simulations capable of reaching timescales and system sizes previously impossible due to catastrophic halts and quantum mechanical divergence. Traditional active learning loops suffer from several critical physical and system constraints that this design aims to decisively overcome. Firstly, the "Time-Continuity Break" issue occurs when the simulation halts due to high uncertainty, forcing the MD to restart from the initial structure after retraining. This completely prevents the observation of long-timescale physical phenomena such as phase transformations or complex diffusion mechanisms. The new objective is to maintain perfect continuity, allowing simulations to pause, update the underlying potential, and resume seamlessly from the exact moment of interruption.

Secondly, the system must overcome "Thermal Noise False Positives." In conventional setups, a single uncertainty threshold governs the halting of the simulation. This makes the system overly sensitive to thermal vibrations—momentary spikes in uncertainty that represent physically harmless noise rather than genuine extrapolation. By establishing a robust two-tier evaluation system, the architecture will mathematically separate benign thermal fluctuations from true structural anomalies that require expensive density functional theory (DFT) validation, thereby drastically reducing unnecessary computational overhead and infinite retraining loops.

Thirdly, the objective addresses "Dangling Bond and Dipole Divergence," a severe limitation in local cluster extraction. When highly uncertain local regions are aggressively excised from a massive bulk simulation and placed into a vacuum for DFT evaluation, the resulting cut surfaces are plagued by unphysical dangling bonds. This leads to massive charge imbalances and dipole moment divergences, which inevitably cause the DFT self-consistent field (SCF) cycles to fail or, worse, to converge on non-physical electronic states (garbage data). The design goal is to strictly enforce "Intelligent Cluster Extraction and Auto-Passivation." This means not just cutting out a region, but meticulously repairing it—automatically passivating cut bonds (e.g., using fractional hydrogen) and relaxing the buffer layers using foundation models (like MACE) before any DFT calculation is attempted. This guarantees that the Quantum Espresso driver only ever sees physically sound, neutrally charged, and structurally relaxed sub-systems.

Fourthly, the system must eradicate "Catastrophic Forgetting and Retraining Bottlenecks." Historically, active learning loops perform full batch retraining upon encountering new structures, which incurs O(N) computational costs that explode over time, while simultaneously degrading the accuracy of previously learned stable bulk structures. The new design mandate is to enforce "Incremental Delta Learning." By utilizing past training history as a replay buffer and leveraging fast surrogate data generation, the system will update the potential in O(1) time complexity, preserving the core stability of the potential while rapidly adapting to new local environments.

Finally, the system must be highly fault-tolerant in High-Performance Computing (HPC) environments. C++ level crashes in LAMMPS must not bring down the Python orchestrator. The architecture will employ robust, task-level checkpointing using an embedded database (like SQLite) to ensure that every expensive calculation is preserved, allowing the system to instantly recover from Slurm wall-time terminations or unexpected node failures without losing progress. All these objectives must be achieved additively; the existing Pydantic configurations, modular drivers, and testing harnesses will be elegantly extended rather than rewritten, ensuring maximum reuse of the current investment.

## 3. System Architecture

The architecture of PyAceMaker revolves around a "Hierarchical Distillation" and "Master-Slave Inversion" paradigm, ensuring that molecular dynamics remains the primary driver of time, while Python-based orchestration and heavy quantum mechanics computations operate asynchronously to support it. The system is composed of several strictly decoupled layers: the Engine Layer, the Evaluation Layer, the Oracle Layer, and the Training Layer.

The Engine Layer is responsible for executing the molecular dynamics simulation. In this new paradigm, we invert the traditional control flow. Instead of Python repeatedly launching short MD runs and checking the output, the LAMMPS C++ loop acts as the master timekeeper. It utilizes the `fix python/invoke` capability to periodically yield execution context to the Python evaluation layer without breaking the internal state of the simulation. If a true structural anomaly is detected, LAMMPS enters a paused state, retaining all atomic coordinates, velocities, and thermodynamic ensembles in memory (or safely dumping a restart file as a robust fallback), while the rest of the orchestration pipeline executes. This ensures perfect time continuity upon resumption.

The Evaluation Layer acts as the gatekeeper. It implements the two-tier uncertainty thresholding. When the engine reports high uncertainty, this layer evaluates whether the spike is merely thermal noise (by checking if the threshold was exceeded for multiple consecutive steps) or a genuine unknown configuration. If it is a true event, the Evaluation Layer triggers the Intelligent Cutout component. This component is strictly responsible for extracting the spatial region of interest, applying a core/buffer force weighting scheme, and immediately passing the raw cluster to the Auto-Passivation module to heal dangling bonds.

The Oracle Layer is a tiered system designed to minimize expensive computations. It consists of the `TieredOracle`, which delegates to either the `MACEManager` (a lightweight, GPU-accelerated foundation model) or the `DFTManager` (Quantum Espresso). When a cluster is extracted, it is first passed to the `MACEManager` for a pre-relaxation of the buffer zone, holding the core fixed. Only when the cluster is physically stabilized is it passed to the `DFTManager` to acquire ground truth forces and energies for the highly uncertain core atoms. The separation of concerns here is absolute: the Oracles know nothing about the MD engine or the extraction logic; they simply receive an `Atoms` object and return calculated properties.

The Training Layer handles the updating of the MLIP. Upon receiving new ground truth data from the DFT oracle, it first fine-tunes the MACE model to awaken it to the specific local chemistry. It then uses this awakened MACE to rapidly generate a cloud of surrogate data around the failed configuration. Finally, the `PacemakerTrainer` combines this surrogate data, the single ground truth DFT calculation, and a sampled replay buffer from the historical SQLite state manager to perform an incremental delta learning update. The newly generated potential is then dynamically reloaded by the LAMMPS engine, and the simulation resumes.

**Rules on Boundary Management and Separation of Concerns:**
1. **Immutability of State:** The `Atoms` objects passed between layers must be treated as immutable by the receivers unless explicitly returned as a new object (e.g., from relaxation). No silent state mutations are permitted.
2. **Abstract Interfaces:** The core orchestrator must only interact with Oracles through the `BaseOracle` interface. It must never directly instantiate a `DFTManager` or `MACEManager`.
3. **No Domain Leakage:** The extraction and passivation utilities must not contain any ML or DFT logic; they purely manipulate geometric and chemical properties based on distance and electronegativity.
4. **Configuration Isolation:** All external commands and paths must be injected via Pydantic configuration models; no hardcoded environment variables or paths are allowed in the business logic.

## 4. Design Architecture

The structural organization of the PyAceMaker repository reflects the strict separation of concerns mandated by the architecture. The `src/pyacemaker/` directory houses the domain logic, configurations, external interfaces, and orchestration utilities. The additive approach ensures that new features seamlessly integrate with existing base classes and utility modules.

```text
src/pyacemaker/
├── core/
│   ├── engine.py       # LAMMPS execution, Seamless Resume, Master-Slave inversion
│   ├── oracle.py       # BaseOracle, TieredOracle, MACEManager, DFTManager
│   └── trainer.py      # PacemakerTrainer, FinetuneManager, Replay Buffer Logic
├── domain_models/
│   ├── config.py       # PyAceConfig master schema
│   ├── dft.py          # DFT Config
│   ├── md.py           # MD Config
│   ├── training.py     # Training Config
│   ├── extraction.py   # NEW: CutoutConfig, ActiveLearningThresholds
│   └── workflow.py     # DistillationConfig, LoopStrategyConfig
├── interfaces/
│   ├── lammps_driver.py# Subprocess or C++ wrapper for LAMMPS

├── utils/

```

**Core Domain Pydantic Models Structure and Typing:**
The configuration schema relies heavily on Pydantic models to ensure absolute type safety and runtime validation. The existing `PyAceConfig` acts as the root object, aggregating smaller, specific configuration models. To support the Next-Generation architecture, we will non-destructively extend the configuration space.

New models to be introduced:
- `ActiveLearningThresholds(BaseModel)`: Captures the two-tier evaluation logic. Fields include `threshold_call_dft` (float), `threshold_add_train` (float), and `smooth_steps` (int) to dictate the consecutive steps required to ignore thermal noise.
- `CutoutConfig(BaseModel)`: Dictates spatial extraction parameters. Fields include `core_radius` (float) for the primary extraction zone, `buffer_radius` (float) for the pre-relaxation zone, `enable_pre_relaxation` (bool), and `enable_passivation` (bool) with `passivation_element` (str, default "H").
- `DistillationConfig(BaseModel)`: Manages Phase 1 zero-shot generation. Contains `mace_model_path` (str), `uncertainty_threshold` (float), and `sampling_structures_per_system` (int).
- `LoopStrategyConfig(BaseModel)`: Governs the training loop behavior. Includes `use_tiered_oracle` (bool), `incremental_update` (bool), `replay_buffer_size` (int), and integrates the `ActiveLearningThresholds`.

**Integration Points and Additive Extensions:**
These new Pydantic schemas will be incorporated into the existing `WorkflowConfig` or directly into `PyAceConfig` as optional fields (or with safe default factories) to ensure backward compatibility.

In `pyacemaker.core.oracle`, the new `MACEManager` and `TieredOracle` classes will inherit from the existing `BaseOracle` interface. This ensures that the main orchestrator can swap out a pure DFT approach for the new tiered approach without any modification to the main control loop. The `TieredOracle` acts as a composite, internally routing `Atoms` objects to `MACEManager` first, assessing the returned uncertainty against the `ActiveLearningThresholds`, and only forwarding to `DFTManager` if the uncertainty exceeds the threshold.

In `pyacemaker.utils.extraction`, the new `extract_intelligent_cluster` function will wrap and extend existing functions like `extract_local_region`. It will sequentially call the extraction, apply the force weights to the `Atoms.info` dictionary, invoke a helper for MACE pre-relaxation, and finally call `_passivate_surface` to inject fractional hydrogen atoms before returning the finalized `Atoms` object. This functional composition guarantees that the complex new behavior is built from simple, testable, and existing primitive operations.

Furthermore, to maintain strict architectural boundaries, the data flow within the system must adhere to immutable principles wherever possible. The core orchestrator acts as the central state machine, reading the unified `PyAceConfig` and dispatching tasks to the respective phase managers. During Phase 1 (Distillation), the orchestrator triggers the combinatorial generator, which produces an initial pool of structures. This pool is immediately handed over to the active set selector, which filters the structures and passes them to the `MACEManager` for confidence evaluation. The high-confidence subset is then serialized and passed to the `PacemakerTrainer` to produce the foundational model. This entire flow is stateless from the perspective of the individual managers; they simply receive data, process it, and return the result. This design ensures that each component can be tested in isolation, mocked during development, and scaled independently on High-Performance Computing clusters using standard parallelization techniques like Dask or Ray, should the need arise in future iterations.

## 5. Implementation Plan

The implementation is strictly divided into six sequential cycles, designed to iteratively build functionality while maintaining an always-deployable state. Each cycle focuses on a specific architectural domain, ensuring that dependencies are resolved before subsequent layers are constructed.

### Cycle 01: Intelligent Cluster Extraction and Passivation Utilities
**Focus:** Building the core geometric and chemical manipulation tools required to safely isolate uncertain regions from massive molecular dynamics snapshots.
**Details:** This cycle focuses entirely on the `utils.extraction` and `utils.embedding` modules. The primary objective is to implement `extract_intelligent_cluster`. We will build the logic to identify the highly uncertain "epicenter" atom, carve out a spherical region defined by `core_radius` and `buffer_radius` (configured via the new `CutoutConfig` Pydantic model), and apply strict `force_weight` properties (1.0 for the core, 0.0 for the buffer and passivated atoms). Following extraction, we will implement the auto-passivation algorithm (`_passivate_surface`), which analyzes cut bonds using covalent radii and electronegativity to automatically attach neutralizing fractional hydrogen atoms. This cycle will also ensure that these extracted clusters are safely embedded into periodic boundary conditions with sufficient vacuum padding to prevent self-interaction during subsequent DFT calculations. No machine learning or MD execution will be implemented in this cycle; the focus is purely on robust data structure manipulation. The logic will strictly enforce that input `Atoms` objects remain unmutated; all extraction functions will return fresh `Atoms` instances. We will extend the internal `neighbor_list` functionality to efficiently compute the local bonding topology necessary for the passivation algorithm. Additionally, we will construct detailed geometric validation helpers to ensure that the appended fractional hydrogens do not unphysically overlap with existing core or buffer atoms. This foundational layer is absolutely critical for the downstream density functional theory (DFT) calculations. Without perfect charge neutrality and relaxed cut surfaces, the Quantum Espresso self-consistent field (SCF) cycles are guaranteed to either diverge or artificially bias the underlying machine learning interatomic potential toward capturing unphysical surface states rather than the intended bulk, defect, or interfacial phenomena. The successful completion of this cycle will directly mitigate the "Dangling Bond and Dipole Divergence" issue identified in the overarching system design objectives. Furthermore, we will create utility wrappers that map standard ASE constraints (like `FixAtoms`) specifically to the defined core region, preparing the structure for the MACE pre-relaxation step that will be introduced in Cycle 02. The entire surface passivation logic will be parameterized, allowing the orchestrator to dynamically select the passivating species (defaulting to fractional hydrogen, but extensible to other dummy atoms or pseudo-potentials depending on the base chemical system). This dynamic parameterization ensures maximum flexibility across entirely different materials classes, such as oxides, nitrides, and complex metallic alloys. To ensure mathematical robustness across edge cases, the algorithm will also feature a projection strategy for passivation vectors: instead of randomly placing hydrogens, the system will extrapolate the vectors from the missing neighbor coordinates, guaranteeing that the local bond angles of the fractured unit cell are perfectly preserved, simulating a truly infinite bulk environment as closely as theoretically possible within a finite cluster approximation.

 The exact algorithm for the spherical carving will utilize the ASE neighbor list initialized with a strictly defined cut-off radius to construct an undirected graph of the local topology. This graph traversal ensures that we correctly identify all bonded nearest neighbors and next-nearest neighbors without arbitrarily cutting strong covalent bonds mid-way, which is a major source of computational instability. We will then construct the `TieredOracle` class. This composite oracle will implement the `BaseOracle` interface and encapsulate the logic defined by `ActiveLearningThresholds`. When a structure is queried, `TieredOracle` will first ask `MACEManager`. If the uncertainty is low, it returns immediately, saving massive computational time. If the uncertainty exceeds the configured threshold, it will fallback to the existing `DFTManager` (Quantum Espresso). **Focus:** Re-architecting the control loop to allow LAMMPS to drive the simulation time while Python handles asynchronous evaluation.

Rather than employing the traditional "run-and-check" paradigm, where the Python process spawns a LAMMPS executable, waits for it to finish or crash, and then reads an external dump file, we are actively embedding the Python evaluation logic directly into the LAMMPS C++ execution loop. This cycle will drastically alter the `core.engine` interface, moving away from synchronous blocking execution and migrating towards an event-driven architecture that responds exclusively to the high-level callbacks yielded by the simulated atomic environment.
