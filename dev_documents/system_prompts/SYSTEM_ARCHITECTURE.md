# System Architecture

## 1. Summary

The PyAceMaker NextGen Hierarchical Distillation Architecture (Version 2.1.0) is a major upgrade to the existing Active Learning pipeline for constructing Machine Learning Interatomic Potentials (MLIPs). The system evolves from a basic orchestration tool into a highly robust, HPC-ready system capable of managing millions of atoms in long-timescale Molecular Dynamics (MD) simulations. It aims to solve critical bottlenecks found in Phase 01: continuity breaks during MD halts, hyper-sensitivity to thermal noise, physical divergence when extracting local atomic clusters, catastrophic forgetting during retraining, and process fragility when interacting with underlying C++ engines like LAMMPS. To achieve this, PyAceMaker integrates FLARE-inspired paradigms such as Master-Slave inversion for seamless MD continuation, a two-tier uncertainty evaluation threshold, intelligent local cluster extraction with passivation, and incremental delta learning for fast model updates. This document defines the structural blueprint, ensuring strict separation of concerns, robust boundary management, and an evolutionary integration path that maximizes the reuse of existing components while introducing new capabilities safely. This system relies heavily on separating the concerns of structure exploration, electronic structure calculations, and machine learning model training into distinct, highly decoupled modules.

## 2. System Design Objectives

The core objectives of the PyAceMaker NextGen Architecture are to enable extreme-scale simulations and automated potential construction without the fragility typically associated with coupled ML/MD workflows. We must achieve these goals while strictly adhering to the architectural principles of separation of concerns, single responsibility, and dependency inversion. The system must be robust, scalable, and physically sound in all its operations, ensuring that the resulting machine learning potentials are both accurate and reliable for long-term production use in advanced materials research.

**1. Seamless Molecular Dynamics Continuity (Master-Slave Inversion):**
The traditional approach of having a Python orchestrator drive LAMMPS via external shell commands leads to severe synchronization issues, state loss when a calculation halts, and immense overhead in data transfer. The new objective is to fundamentally invert this control flow. The LAMMPS C++ execution loop will run continuously, acting as the master process. It will occasionally invoke a Python callback (via `fix python/invoke`) to evaluate the current uncertainty of the system using the fast foundation model. If the uncertainty is high, the simulation pauses its integration natively, updates the potential in the background through the orchestrator, reloads the coefficients, and resumes without ever losing atomic coordinates, velocities, or thermostat state. This ensures that long-timescale phenomena like phase transformations, grain boundary migration, or complex defect diffusion are not artificially interrupted or reset by retraining events.

**2. Thermal Noise Resilience (Two-Tier Thresholds):**
A single threshold for uncertainty evaluation often leads to catastrophic false positives triggered by normal, physically safe thermal vibrations. This causes the system to halt needlessly, wasting immense computational resources on redundant DFT calculations. The objective is to decouple the halt criteria from the extraction criteria. We introduce a robust Two-Tier Threshold system. The `threshold_call_dft` is a higher threshold that must be sustained over several consecutive steps to determine if a full halt and Density Functional Theory (DFT) calculation are truly necessary. Conversely, the `threshold_add_train` is a lower threshold used purely to identify the specific atoms whose local environments need to be added to the training set once a halt is triggered. This drastically reduces unnecessary computational overhead and prevents the infinite loop of retraining on thermal noise.

**3. Physical Robustness in Local Extraction (Intelligent Cutout & Passivation):**
When a highly uncertain region is discovered within a massive MD cell (e.g., a million atoms), extracting it directly into a vacuum creates severe physical artifacts. It introduces numerous dangling bonds at the cut surfaces, causing massive charge imbalances and dipole moment divergence. This inevitably causes the subsequent DFT calculation's Self-Consistent Field (SCF) loop to fail entirely, or worse, forces the model to learn unphysical "garbage" electronic states. The objective is to intelligently extract the "epicenter" of uncertainty alongside a substantial buffer region. The core atoms are strictly frozen, the buffer is pre-relaxed using the foundational MACE model to remove extraction strain, and the surface is automatically passivated using dummy atoms (e.g., fractional hydrogen) to maintain perfect charge neutrality before any expensive DFT calculation occurs. To optimize performance, the extraction algorithm must utilize an $O(\log N)$ KDTree rather than naive neighbor lists, enabling rapid querying even in million-atom systems.

**4. O(1) Training Cost and Memory Management (Incremental Updates):**
Retraining the machine learning potential from scratch on all historical data at every single halt leads to a rapid computational explosion. Furthermore, constantly appending highly distorted error structures to the dataset degrades the model's accuracy on stable bulk structures—a phenomenon known as catastrophic forgetting. The system must implement robust delta learning strategies (fitting to the difference from a physical baseline like a Lennard-Jones or ZBL potential) and incremental updates. This involves fine-tuning from the previous potential state while mixing in a carefully curated replay buffer of historical data. This ensures that the cost of updating the potential remains strictly constant O(1), regardless of how long the simulation runs or how much data is accumulated.

**5. HPC Resilience and Scale (Robust State Management):**
The system must be absolutely fault-tolerant in volatile High-Performance Computing (HPC) environments. If a massive parallel job hits a strict wall-time limit, or if a compute node catastrophically crashes, the system must not lose days of progress. Fine-grained checkpointing is strictly required. The architecture defines a **Repository Pattern** interface (`BaseCheckpointRepository`) to abstract state persistence. For massive scalability, we avoid standard SQLite files (which suffer from MPI locking issues) in favor of distributed stores or append-only JSON-lines (`.jsonl`) logs. Furthermore, the system must aggressively clean up massive computational artifacts (like Quantum Espresso `.wfc` wavefunction files or massive LAMMPS trajectory dumps) to prevent catastrophic storage exhaustion on shared HPC filesystems, while running independent calculation tasks asynchronously using modern dispatcher patterns. Crucially, foundation models like MACE must be memory-resident (e.g., pre-loaded in VRAM as a singleton daemon) to avoid catastrophic I/O bottlenecks during the billions of uncertainty evaluations required.

## 3. System Architecture

The architecture relies on strict boundary management to separate orchestration, calculation, and learning logic. The system uses a centralized `Orchestrator` that delegates tasks to specialized Managers (`OracleManager`, `EngineManager`, `TrainerManager`). This ensures that the orchestrator itself remains lightweight and purely focused on workflow transitions, while the heavy lifting is handled by dedicated, highly cohesive modules.

**Boundary Management and Separation of Concerns:**
1.  **Data Isolation:** Data flows in a strictly unidirectional manner during the Active Learning loop to prevent state corruption. The MD Engine produces continuous atomic trajectory streams. The Oracle Evaluator assesses these streams and generates labeled data when necessary. The Trainer consumes these labels to produce an updated interatomic potential. The Engine then consumes the new potential. Modules absolutely do not share internal state variables; they communicate strictly through standardized, immutable `Atoms` objects and explicitly passed, validated Pydantic configuration objects.
2.  **Dependency Injection:** External dependencies and heavy computational drivers (LAMMPS, Quantum Espresso, MACE, Pacemaker) are completely abstracted behind robust `BaseEngine`, `BaseOracle`, and `BaseTrainer` abstract interfaces. The core logic in the orchestrator is blissfully unaware of which specific tool is currently running underneath, knowing only the rigid contract it must fulfill. This allows for seamless swapping of underlying physics engines without touching the orchestration logic.
3.  **Additive Extension:** Existing modules within the `src/pyacemaker/` directory, such as `utils.extraction` and `core.oracle`, must be extended via subclassing or adding new pure functions. Existing legacy workflows must remain fully functional; new NextGen features are explicitly enabled via specific flags within the strictly typed configuration models. We must never break the existing API contract for Phase 01 users.

## 4. Design Architecture

The design explicitly ensures that complex domain concepts are codified as robust, strictly typed Pydantic models. This guarantees complete type safety and profound configuration validation at the absolute boundaries of the system before any expensive execution begins. We heavily employ a "functional core, imperative shell" design pattern to ensure that complex physics operations (like cluster extraction, surface passivation, and KDTree generation) are isolated as pure functions, making them easily testable without spinning up massive, slow engine environments.

### File Structure (Ascii Tree)

```text
src/pyacemaker/
├── core/
│   ├── engine.py       # LammpsEngine, Stateless Engine interfaces, C++ callbacks
│   ├── oracle.py       # TieredOracle, MACEManager, DFTManager, Retry logic
│   └── trainer.py      # PacemakerTrainer, FinetuneManager, Delta Learning Extxyz concatenation
├── domain_models/
│   ├── config.py       # Main configuration entry points, Project defaults
│   └── workflow.py     # DistillationConfig, ActiveLearningThresholds, CutoutConfig, LoopStrategyConfig
├── utils/

│   └── structure.py    # General Atoms manipulation, Cell standardizations
├── orchestrator.py     # Hierarchical Distillation Loop Finite State Machine
└── main.py             # CLI entry point and environment setup
```

### Core Domain Pydantic Models Structure and Typing

The system introduces several new, highly specific Pydantic models within `src/pyacemaker/domain_models/workflow.py` to handle the intricate needs of the NextGen architecture. These models are meticulously designed to be imported safely by other modules (like `config.py` and `md.py`) without causing circular dependencies or Pydantic rebuild errors. They leverage rigorous field validators to enforce cross-parameter logical consistency.

*   `DistillationConfig`: Configures Phase 1 (Zero-Shot Distillation) operations. Contains critical parameters like `enable` (bool), `mace_model_path` (str), `uncertainty_threshold` (float), and `sampling_structures_per_system` (int). It integrates directly into the main `WorkflowConfig` hierarchy.
*   `ActiveLearningThresholds`: Defines the complex two-tier evaluation logic. Contains `threshold_call_dft` (float) for halting the engine, `threshold_add_train` (float) for atomic selection, and `smooth_steps` (int) to buffer against thermal noise. This entirely replaces the outdated single-threshold logic in existing engine configurations. A model validator strictly enforces that `threshold_add_train < threshold_call_dft`.
*   `CutoutConfig`: Defines the precise physical parameters for intelligent local extraction. Contains `core_radius` (float), `buffer_radius` (float), `enable_pre_relaxation` (bool), and `enable_passivation` (bool), along with `passivation_element` (str, typically "H" or a fractional pseudopotential).
*   `LoopStrategyConfig`: Configures the overarching active learning loop state machine strategy. Contains `use_tiered_oracle` (bool), `incremental_update` (bool), `replay_buffer_size` (int), and `baseline_potential_type` (str, e.g., "LJ", "ZBL"). A complex field validator guarantees that `replay_buffer_size` is strictly strictly positive (> 0) whenever `incremental_update` is set to `True`.

These new configuration objects are safely composed into the master `ProjectConfig` object, extending the existing validation schemas seamlessly. By using modern Pydantic features, we guarantee that the simulation environment is perfectly sound before a single compute cycle is spent.

## 5. Implementation Plan

The project is decomposed into exactly 5 sequential cycles to ensure stable integration, rigorous testing, and continuous delivery of architectural milestones. Each cycle builds strictly upon the verified foundation of the previous one. The boundaries and APIs are strictly defined to eliminate ambiguity for the implementing developers.

**Cycle 01: Domain Models and Zero-Shot Distillation Infrastructure**
The primary goal of this foundational cycle is to establish the core data structures and execute the entire Phase 1 workflow without touching the legacy codebase. We begin by defining the exact Pydantic schemas in `workflow.py`. For example, the `LoopStrategyConfig` will include a critical field validator: `@model_validator(mode='after')` to verify `replay_buffer_size > 0 if self.incremental_update else True`. Once the schemas are integrated seamlessly into the master `ProjectConfig`, we architect the `MACEManager` class extending the `BaseOracle` interface within `core.oracle`. This class must establish a memory-resident PyTorch session utilizing GPU acceleration if available, accepting an `Atoms` list and returning a tuple `(energies, forces, uncertainties)`. With the Oracle prepared, we script the zero-shot distillation logic. We use standard combinatorial functions to generate single-element and binary structural arrays (including diverse stoichiometries and deliberately introduced vacancies). The `ActiveSetSelector` leverages its D-optimality matrix operations to reduce a pool of 100,000 generated structures to 1,000 highly informative candidates. The memory-resident `MACEManager` filters out structures where MACE uncertainty exceeds `DistillationConfig.uncertainty_threshold`. Finally, the filtered dataset is directly funneled into the existing trainer module to output the baseline potential, crucially utilizing Lennard-Jones parameters to guarantee repulsive stability at short atomic distances. All this occurs without invoking Quantum Espresso once.

**Cycle 02: Tiered Oracle and Intelligent Cluster Extraction**
This cycle focuses heavily on the extreme physics requirements of Phase 3, establishing the safety boundaries for local defect extraction. We implement the `TieredOracle` which acts as a sophisticated router; its `evaluate()` signature intercepts requests, forwards them to the fast MACE model, and only conditionally delegates to the massive `DFTManager` if the max uncertainty breaches `threshold_call_dft`. The absolute most critical component developed here is the pure algorithmic function `utils.extraction.extract_intelligent_cluster(structure: Atoms, target_atoms: List[int], config: CutoutConfig) -> Atoms`. To circumvent the massive $O(N^2)$ overhead of ASE's default neighbor lists on million-atom systems, this function must strictly instantiate a `scipy.spatial.cKDTree` mapping the atomic coordinates. We define the epicenter via `target_atoms`, query the KDTree for all indices within `core_radius`, tag them with `force_weight=1.0`, and freeze them via `ase.constraints.FixAtoms`. A secondary KDTree query captures atoms within `core_radius + buffer_radius`, tagging them `force_weight=0.0`. The `MACEManager` then executes an LBFGS optimization solely on the unconstrained buffer atoms to alleviate boundary strain. Finally, the critical `_passivate_surface` algorithm identifies missing coordination numbers at the boundary and injects dummy passivation atoms (e.g., fractional hydrogen). The API boundary here mandates a strict distance check—passivation atoms must absolutely never be inserted closer than 0.8 Angstroms to any frozen core atom to prevent catastrophic wavefunction overlap in the subsequent DFT.

**Cycle 03: Incremental Delta Learning and Training Upgrades**
This cycle completely overhauls the Phase 4 learning logic to permanently cure catastrophic forgetting while maintaining strict O(1) computational cost. We substantially upgrade the `PacemakerTrainer` within `core.trainer`. The explicit API contract requires the trainer's `train(new_data: List[Atoms])` method to intelligently concatenate data. Instead of rebuilding from scratch, it opens the historical `training_history.extxyz` file, randomly samples `replay_buffer_size` structures (e.g., 500 stable bulk and older defect configurations), and appends the newly computed DFT `Atoms` objects to form a hybrid training batch. We implement a dedicated configuration generator that writes an `input.yaml` specifically demanding Delta Learning parameters (`fit_baseline: true`, `baseline_potential: LJ`) and pointing to the previous generation's `.yace` model weights as the initialization point. The subprocess command is constructed meticulously to ensure the new model is a mathematical refinement of the old. Simultaneously, we implement the `FinetuneManager` interface, giving it the specific capability to freeze the embedding layers of the underlying MACE PyTorch model, allowing ultra-fast backpropagation exclusively on the linear readout layers using the precise newly acquired `Atoms` batch. This "awakens" the foundation model to the specific interfacial physics of the halt event before it generates thousands of fast surrogate structures to assist the ACE potential fitting.

**Cycle 04: Master-Slave Inversion and Seamless Engine Resume**
This cycle directly tackles the hardest integration challenge: binding the high-level Python logic directly into the low-level LAMMPS C++ execution loop without losing process state. We overhaul the `LammpsEngine` execution model to support continuous integration paradigms. We discard the legacy `subprocess.Popen` execution which loses total memory state upon exit. Instead, we implement true Master-Slave resume logic. We introduce two paths. Path A utilizes LAMMPS's native `fix python/invoke` capability, allowing the C++ integrator to call a registered Python callback function every `N` steps, passing the forces and coordinates in memory to Python for immediate uncertainty evaluation via the memory-resident MACE model. Path B (the robust fallback for HPC systems lacking Python-linked LAMMPS binaries) involves building a `StatelessEngine` watcher. This engine monitors a designated output folder. LAMMPS is instructed via a custom `thermo_style` to dump a specifically formatted "uncertainty signal" file. When the Python orchestrator detects this file, it commands LAMMPS to halt, write a binary `.restart` file, and terminate gracefully. After the PyAceMaker orchestrator finishes updating the potential via Phase 4, it generates a perfect resumption script specifically containing the commands `reset_timestep no` and `velocity all scale ${temp}` before issuing the `read_restart` command. This stringent API boundary guarantees that the MD engine resumes its precise trajectory, specific atomic velocities, and exact thermostat state without introducing chaotic energy spikes. The two-tier uncertainty mathematical logic (`threshold_add_train` vs `threshold_call_dft` sustained over `smooth_steps`) is coded directly into the evaluator callback to filter thermal noise.

**Cycle 05: Hierarchical Loop Orchestration and HPC Robustness**
The final, culminating cycle integrates all independently verified components into a master, fully automated Finite State Machine (FSM) inside `orchestrator.py`. The Orchestrator's internal architecture is refactored from a simple `while` loop into a strict FSM traversing the explicit states: `DISTILLING`, `MD_RUNNING`, `HALTED`, `VALIDATING`, `EXTRACTING`, and `INCREMENTAL_TRAINING`. This rigid structure prevents impossible transitions (e.g., extracting a cluster without halting first). Furthermore, we implement the required enterprise HPC robustness features. The architecture defines a `BaseCheckpointRepository` interface to abstract state persistence. For massive HPC deployment, we avoid standard SQLite databases to prevent severe MPI file-locking contention. We build a `JsonLinesRepository` implementation that strictly appends serialized Pydantic state objects to a local `.jsonl` file after every successful FSM transition. This absolutely guarantees survival against random Slurm job timeouts or node hardware failures; upon restart, the Orchestrator rapidly reads the `.jsonl` file to instantly restore the last valid FSM state. Finally, we implement a background `ArtifactCleanupDaemon` running in an isolated Python thread. Its single responsibility is to monitor the workspace directory and execute `os.remove()` or `tar -czf` on massive files like Quantum Espresso `.wfc` wavefunctions or massive LAMMPS `.dump` trajectories immediately after the relevant state transition is complete. This ensures the workflow never blocks the main orchestration thread while preventing catastrophic storage exhaustion on shared multi-terabyte HPC filesystem quotas.

## 6. Test Strategy

Testing must rigorously verify the physical, mathematical, and computational validity of the new architecture without ever relying on live, highly expensive external quantum or MD engine calls during Continuous Integration (CI) test suite runs. All tests must be absolutely free of external side effects, heavily utilizing standard `tempfile` modules or `pytest` `tmp_path` fixtures for strict I/O isolation, and intelligent mocking libraries to bypass multi-hour calculations, ensuring the entire test suite runs reliably in milliseconds.

**Cycle 01: Domain Models and Zero-Shot Distillation Infrastructure**
*   **Unit Tests:** We will strictly validate all newly defined Pydantic models. We will write explicit test cases targeting custom field validators; for example, we will intentionally initialize an `ActiveLearningThresholds` instance where `threshold_add_train` is $0.08$ and `threshold_call_dft` is $0.05$. We will use `pytest.raises(ValidationError)` to strictly assert that the Pydantic parser correctly intercepts and rejects this physically invalid configuration. We will verify that the `MACEManager` class correctly formats the input tensors required by the MACE API and handles missing optional GPU dependencies gracefully by falling back to the CPU without throwing fatal runtime exceptions.
*   **Integration Tests:** We will completely mock the MACE model's `__call__` response using `unittest.mock.MagicMock`. We will then execute the complex zero-shot distillation loop and rigorously verify that it correctly invokes the combinatorial structure generators, filters the massive output pool strictly based on the mock uncertainty arrays returned by our fake MACE object, and successfully initiates a call to the Pacemaker training task manager, verifying the exact number of `Atoms` objects passed in the payload list.

**Cycle 02: Tiered Oracle and Intelligent Cluster Extraction**
*   **Unit Tests:** We will comprehensively and exhaustively test the pure algorithmic `extract_intelligent_cluster` function. We will construct predefined, highly specific `Atoms` objects representing known periodic boundary conditions (e.g., a simple cubic lattice). We will invoke the function and strictly assert that the KDTree algorithm correctly identifies the geometric shell. We must mathematically verify that the returned core atoms are precisely tagged with the `force_weight=1.0` numpy array and are perfectly constrained by the ASE `FixAtoms` class. We must assert that buffer atoms are correctly tagged `force_weight=0.0`. Most critically, we will test the `_passivate_surface` logic to ensure it adds the exact stoichiometric number of neutralizing dummy atoms based on standard valency rules, and we will assert that the calculated Euclidean distance between any dummy atom and any core atom is strictly greater than the $0.8$ Angstrom minimum safety boundary.
*   **Integration Tests:** We will meticulously test the `TieredOracle` routing state machine logic. By injecting a mocked `MACEManager` and a mocked `DFTManager`, we will verify that invoking the Oracle's `evaluate()` method immediately returns the fast MACE results when uncertainty is artificially clamped below the threshold. Conversely, we will verify that it correctly and automatically delegates the computation task to the mocked DFT engine exactly when the simulated uncertainty is intentionally spiked above the strict upper configuration limit.

**Cycle 03: Incremental Delta Learning and Training Upgrades**
*   **Unit Tests:** We will rigorously test the highly complex `PacemakerTrainer` YAML configuration generation logic. We will invoke the generator, parse the resulting raw YAML string using the `yaml` library, and write assertions to ensure the dictionary correctly contains all specifically mandated incremental learning flags (e.g., `fit_baseline` must strictly equal `True`), that the `replay_buffer_size` parameter is present and accurate, and that the file paths pointing to the baseline LJ potential are syntactically perfect without any trailing whitespace or formatting errors.
*   **Integration Tests:** We will mock the external command-line `pace_train` execution call utilizing Python's `subprocess.run` mock patches. We will provide the test environment with a mock array of new active `Atoms` data and a simulated historical `.extxyz` file on disk representing the replay buffer. We will assert that the trainer's concatenation logic correctly reads, samples, and merges the datasets within a secure, isolated temporary directory. We will finally inspect the `call_args_list` of the subprocess mock to verify that the training command was initiated with the absolute correct bash arguments, paths, and environment variables required for a safe delta learning run.

**Cycle 04: Master-Slave Inversion and Seamless Engine Resume**
*   **Unit Tests:** We will rigorously mathematically test the two-tier threshold evaluation and smoothing logic decoupled from any engine. We will write unit tests that feed the evaluator mock Numpy arrays of uncertainty values containing sudden, massive isolated spikes (perfectly simulating random thermal noise collisions) interspersed alongside sustained high-value plateaus. We will write strict assertions verifying that the boolean halt signals are never triggered by the isolated spikes, but only fire when the sustained plateau length strictly exceeds the `smooth_steps` configuration integer boundary.
*   **Integration Tests:** We will construct a minimal, extremely fast-executing LAMMPS script utilizing a highly simplified mock Lennard-Jones pair style. We will execute the script using the Python interface and intentionally issue a programmatic halt command halfway through the simulation trajectory. We will then invoke the engine's resume capability. By parsing the thermodynamic output logs, we will assert that the engine was successfully restarted using the exact saved binary state (verifying identical coordinates, atomic velocities, and precise simulation box dimensions) from the exact picosecond of interruption. We will plot the total thermodynamic energy profile to verify mathematical continuity and ensure no explosive energy spikes occurred upon resumption.

**Cycle 05: Hierarchical Loop Orchestration and HPC Robustness**
*   **Unit Tests:** We will strictly unit test the `JsonLinesRepository`. By providing mock Pydantic state objects, we will verify that the repository correctly appends the serialized JSON strings to the disk file. We will then simulate a full system restart and verify that the `load_latest_state()` method perfectly reconstructs the complex Pydantic configuration object exactly as it was saved, guaranteeing lossless data persistence.
*   **Integration/E2E Tests:** We will execute a complete, entirely mocked end-to-end orchestration loop utilizing a mock driver for the MD engine and Oracle. We will aggressively verify the massive Orchestrator state machine correctly and safely transitions precisely through its expected lifecycle states (`DISTILLING` -> `MD_RUNNING` -> `HALTED` -> `EXTRACTING` -> `INCREMENTAL_TRAINING`). To prove absolute robustness, we will intentionally raise a severe `RuntimeError` manually deep within the `EXTRACTING` state. We will catch this error, discard the orchestrator object in memory, instantiate a completely new orchestrator instance targeting the same working directory, and write explicit assertions verifying that it reads the `.jsonl` log and immediately resumes processing the specific extraction task exactly where it crashed, rather than destructively restarting the entire multi-day simulation sequence from the absolute beginning. Finally, we will invoke the `ArtifactCleanupDaemon` against a directory containing 1-gigabyte mock `.wfc` files, asserting they are swiftly deleted from the filesystem without raising asynchronous thread exceptions.
