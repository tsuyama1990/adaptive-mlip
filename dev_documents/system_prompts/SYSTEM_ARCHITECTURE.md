# PYACEMAKER System Architecture

## 1. Summary
PyAceMaker is an advanced orchestration platform designed to automate the construction of robust Machine Learning Interatomic Potentials (MLIPs). The system orchestrates an active learning loop utilizing a "Hierarchical Distillation" architecture. This methodology directly addresses the critical challenges of long-timescale molecular dynamics simulations. Through intelligent integration with foundation models, primarily MACE, and highly accurate First-Principles calculations via Quantum ESPRESSO, PyAceMaker significantly reduces computational overhead. By incorporating best practices from architectures like FLARE, the system enables continuous, disruption-free molecular dynamics, robust uncertainty quantification, and seamless, incremental potential updates without catastrophic forgetting.

## 2. System Design Objectives
The primary design objective of the next-generation PyAceMaker architecture is to enable continuous, large-scale, and long-timescale molecular dynamics (MD) simulations by overcoming the physical and system limitations identified in Phase 01. The legacy implementation suffered from several fatal flaws when scaled to HPC environments (simulating tens of thousands to millions of atoms over extended durations). These flaws included broken time-continuity during uncertainty halts, oversensitivity to thermal noise leading to false positives, physical divergence due to naive local cluster extraction (dangling bonds and dipole moments), and sluggish batch retraining procedures that precipitated catastrophic forgetting of stable bulk structures. Moreover, the tight coupling between the Python orchestrator and the underlying LAMMPS C++ engine resulted in system fragility, where C++ level crashes would indiscriminately terminate the entire stateful learning loop.

To rectify these profound issues, the new architecture integrates four paradigm shifts inspired by the FLARE framework's best practices. The first and most critical objective is the "Inversion of Control" or Master-Slave reversal. Instead of Python dictating the execution flow of LAMMPS externally, LAMMPS's internal C++ loop will govern the integration via `fix python/invoke` or robust restart file mechanisms. This ensures that when the system encounters high uncertainty, the MD simulation can pause, update the interatomic potential in the background, and resume seamlessly from the exact same timestep, coordinate configuration, and velocity distribution. This unbroken time-continuity is absolutely paramount for observing slow physical phenomena such as phase transformations and atomic diffusion.

The second major objective is the implementation of a "Two-Tier Threshold" system for uncertainty evaluation. By decoupling the threshold required to halt the MD simulation (`threshold_call_dft`) from the threshold used to select atoms for the training dataset (`threshold_add_train`), the system becomes remarkably resilient to transient thermal noise. Only sustained, consecutive breaches of the primary threshold will trigger a computational halt, eliminating the infinite loops caused by harmless thermal spikes.

The third objective revolves around the principle of "Global Calculation, Local Learning." When the system halts due to genuine physical uncertainty (e.g., an unencountered defect or collision cascade), the architecture must intelligently extract a minimal, yet physically complete, local cluster around the epicenter of uncertainty. This extraction process must go beyond simple spatial clipping. It requires rigorous, automated passivation techniques—such as appending fractional hydrogen atoms to dangling bonds—and pre-relaxation of the boundary layer using the MACE foundation model while freezing the core atoms. This ensures that the subsequent high-fidelity Quantum ESPRESSO (DFT) calculations converge reliably on a physically meaningful, electrically neutral state, preventing the injection of "garbage" non-physical forces into the learning pipeline.

Finally, the fourth objective is the transition from batch retraining to "Incremental Update" strategies. The system will abandon the computationally explosive practice of retraining the entire potential from scratch at every active learning step. Instead, it will leverage past weights as initializations for delta learning. By maintaining a carefully curated replay buffer of historical data and blending it with dynamically generated surrogate data from a fine-tuned "awakened" MACE model, the system can perform rapid, O(1) computational updates. This incremental approach not only accelerates the turnaround time between MD pauses but fundamentally prevents the catastrophic forgetting of the stable baseline configurations established during the initial zero-shot distillation phase. By satisfying these objectives, PyAceMaker will achieve an unprecedented level of autonomy, stability, and physical fidelity in autonomous materials discovery workflows.

## 3. System Architecture
The PyAceMaker architecture is built upon a state-machine driven orchestration model that emphasizes modern software design patterns, particularly Dependency Injection and strict Separation of Concerns. The system is structurally divided into four distinct phases, each managed by specialized orchestrator components that interact through rigorously typed Pydantic data models. This modular design ensures that complex scientific computing tasks are decoupled, testable, and robust against failures in external dependencies like HPC schedulers or tightly integrated C++ libraries.

At the core of the architecture is the concept of "Hierarchical Distillation." The data flow begins with Phase 1: Zero-Shot Distillation. The `Combinatorial Generator` synthesizes a massive pool of diverse structural variants, including distortions, rattlings, and stoichiometric defects. To maximize information density while minimizing computational cost, the `ActiveSet Selector` (utilizing DIRECT sampling) curates a representative subset. This subset is then evaluated by the `MACEManager Oracle`, a foundation model that provides energies, forces, and crucial uncertainty metrics. Only high-confidence predictions are passed to the `Pacemaker Trainer` to construct the baseline ACE potential via Lennard-Jones delta learning. This phase establishes the fundamental physical baseline without requiring a single expensive DFT calculation.

Phase 2 acts as the critical validation gate. The `Validator Subsystem` rigorously tests the baseline potential against core physical properties (elastic constants, phonon dispersions) and executes a miniature MD stress test. Success here transitions the architecture into the active learning loop (Phases 3 and 4).

During the active MD run, the Master-Slave relationship takes precedence. The LAMMPS engine runs autonomously, periodically calling the `Two-Tier Evaluator` via Python callbacks. When sustained uncertainty triggers a halt, the `Intelligent Cutout` component springs into action. This component is strictly responsible for spatial isolation, relying on the `MACE Oracle` for boundary pre-relaxation and the `Auto Passivation` module for electrical neutralization. The physically sanitized cluster is then dispatched to the `DFTManager` for absolute ground-truth force evaluation.

The final architectural leg is Phase 4: Hierarchical Delta Learning. The newly acquired DFT data is first used to fine-tune the MACE foundation model, creating an "awakened" Oracle specifically attuned to the encountered localized physics. This awakened MACE then generates thousands of surrogate data points within the local phase space. The `Incremental Trainer` blends this surrogate data with a historical replay buffer, executing a rapid delta-update on the ACE potential. Crucially, the orchestrator then signals the LAMMPS engine to reload the updated potential and seamlessly resume the simulation from the exact suspended state.

**Boundary Management and Separation of Concerns:**
1. **State vs. Execution:** The Orchestrator manages the workflow state (persisted via SQLite) but delegates all heavy computation to external drivers (DFT, MLIP training) via asynchronous dispatches.
2. **Configuration Immutability:** All configurations are validated once at startup via Pydantic models with `extra="forbid"`. Internal components receive read-only configuration objects, preventing side-effect configuration drift.
3. **Oracle Abstraction:** The `BaseOracle` interface completely decouples the Orchestrator from the underlying prediction engine (MACE vs. QE). The `TieredOracle` handles routing logic, ensuring the Orchestrator remains agnostic to whether a force was predicted by AI or computed via DFT.
4. **Sandbox Isolation:** All external commands (e.g., LAMMPS scripts, `pw.x` executions) are executed within isolated, temporary working directories managed by specific drivers. This prevents cross-contamination of artifacts and ensures parallel safety.

## 4. Design Architecture
The design architecture of PyAceMaker emphasizes a modular, deeply nested hierarchy that strictly isolates domain logic from infrastructure execution. The project follows a functional core, imperative shell methodology, where the core domain models (Pydantic) dictate the state and the orchestrator interfaces execute the side effects. This architecture is designed to accommodate complex operations without letting business logic bleed into low-level execution details. We ensure all modifications add to existing capabilities rather than destroying established patterns. The entire system is built to minimize any form of tightly coupled logic that could create unmaintainable God Classes. The core structure is defined below. The implementation will reuse all existing `core.oracle` and `interfaces` objects.

**File Structure Overview:**
```text
pyacemaker/
├── src/pyacemaker/
│ ├── core/
│ │ ├── engine.py # LAMMPS integration and Master-Slave logic
│ │ ├── oracle.py # BaseOracle, MACEManager, TieredOracle
│ │ ├── trainer.py # FinetuneManager, PacemakerTrainer (Incremental)
│ │ └── validator.py # Phase 2 physics validation logic
│ ├── domain_models/
│ │ ├── config.py # Core Pydantic configuration schemas
│ │ └── state.py # Workflow checkpointing schemas
│ ├── interfaces/
│ │ ├── lammps_driver.py# Low-level LAMMPS command execution
│ │ ├── qe_driver.py # Quantum Espresso input generation and parsing
│ │ └── mace_driver.py # MACE PyTorch model initialization and execution
│ └── utils/
│ ├── extraction.py # extract_intelligent_cluster logic
│ ├── structure.py # Atom manipulation and passivation
│ └── embedding.py # Vacuum and PBC adjustments
```

**Core Domain Pydantic Models Structure and Typing:**
The configuration schema is strongly typed using Pydantic V2, ensuring that all hyperparameters are validated prior to execution. The new architecture extends the existing domain objects additively, ensuring that old configurations still parse safely if required, but new features have explicit typed backing. Each model is designed strictly and securely to forbid extra variables and guarantee correctness at the very perimeter of the system. We ensure clear integration points on how new schemas extend existing domain objects without breaking compatibility.

1. `DistillationConfig`: Governs Phase 1. It defines the foundation model path (`mace_model_path: str`), the confidence threshold for zero-shot distillation (`uncertainty_threshold: float`), and the initial combinatorial sampling density (`sampling_structures_per_system: int`). This integrates into the existing global configuration as a new, optional nested block within the main configuration object.
2. `ActiveLearningThresholds`: Represents the FLARE-inspired two-tier evaluation system. It contains `threshold_call_dft: float` (for halting MD), `threshold_add_train: float` (for atomic force weighting), and `smooth_steps: int` (the temporal noise filter). This systematically replaces the legacy, singular `uncertainty_threshold` parameter in the active learning loop settings, providing backward compatibility through deprecation warnings if the old singular value is provided.
3. `CutoutConfig`: Controls Phase 3 intelligent extraction. It dictates the spatial geometries: `core_radius: float` and `buffer_radius: float`. It also toggles boolean flags for `enable_pre_relaxation` and `enable_passivation`, and sets the default `passivation_element: str` (typically "H"). This is a completely new schema object extending the extraction utilities configuration block.
4. `LoopStrategyConfig`: Defines the high-level orchestration behavior. It includes flags like `use_tiered_oracle: bool` and `incremental_update: bool`. Crucially, it manages catastrophic forgetting via `replay_buffer_size: int` and sets the `baseline_potential_type: str`. This object sits at the root of the workflow execution configuration.

**Integration Points:**
The new Pydantic models extend the existing codebase purely via composition. The `LoopStrategyConfig` will be injected into the existing `Orchestrator` class initialization perfectly. The `ActiveLearningThresholds` will be consumed safely by a new `TwoTierEvaluator` callback class, which intercepts the existing LAMMPS output stream dynamically. The `CutoutConfig` directly parameterizes the newly expanded `utils.extraction.extract_intelligent_cluster` function, allowing the perfectly existing `DFTManager` to remain completely unaware of the complex geometric manipulations performed exactly prior to its invocation, ensuring perfect modularity.
