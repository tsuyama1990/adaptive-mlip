# Cycle 06: Automated Preflight Diagnostics

## Summary
The primary objective of Cycle 06 focuses on establishing the highly robust, automated preflight evaluation layer bridging the gap between the configuration intent and the active learning thresholds. This specifically requires the development of the `pyacemaker.core.preflight` module and its strict flawless integration with the existing robust `pyacemaker.domain_models.compiler` logic.

By completing Cycle 06, the system mathematically enables non-expert engineers to dynamically set highly complex real-time physical simulation trajectory configurations natively without risking catastrophic failure hours into a run. Before committing substantial cloud computing resources or initiating massive GPU-accelerated MACE evaluations, the "Run 0 Validation" diagnostic ensures that the user's intent—as compiled into the `WorkflowConfig`—is physically sound. It verifies that atomic structures do not contain overlapping coordinates (which would immediately crash LAMMPS), that MACE models are accessible and correctly formatted, and that the requested DFT pseudopotentials match the elements present in the system.

This preflight mechanism is essential for a cloud-based Software-as-a-Service (SaaS) architecture where users cannot manually inspect terminal output. It provides instantaneous, actionable feedback to the React GUI, allowing users to correct their workflow design before they incur computational costs. This cycle is the final gatekeeper, translating potential runtime errors into safe, compile-time validation rejections, fulfilling the promise of an "Intent-Driven" interface by preventing user frustration. The preflight checks not only analyze static dependencies and file paths but also perform a minimal physics test, essentially a "dry run" of the initial state, to confirm the thermodynamic and geometric stability of the system before the main orchestrator loop assumes control.

This phase is critical for the perceived quality of the PyAceMaker platform. When complex active learning simulations fail, the error messages generated by the underlying C++ or Fortran codes (LAMMPS and Quantum ESPRESSO, respectively) are notoriously cryptic, often involving segmentation faults or generic "Lost Atoms" warnings. By intercepting these failures in Python during the preflight phase, the system can translate these cryptic failures into actionable, domain-specific guidance (e.g., "The initial distance between Atom 14 and Atom 15 is 0.2 Angstroms, which is unphysically small for a metallic bond. Please relax the initial structure before initiating the active learning loop"). This drastically reduces the cognitive load on the user and minimizes the time wasted on debugging basic setup errors, allowing the researcher to focus entirely on the scientific outcomes.

## System Architecture
The implementation aligns with the complete architecture mapping mathematical trajectory parameters. We introduce `pyacemaker.core.preflight` entirely. The `pyacemaker.core.preflight` acts as the functional mathematical evaluation, converting the perfectly abstract `WorkflowConfig` exactly objects into mathematically correct initialization streams.

```text
src/pyacemaker/
├── api/                       # [EXISTING]
├── core/
│   ├── orchestrator.py        # [MODIFIED] Preflight invocation
│   └── preflight.py           # [NEW] Highly accurate preflight routines
└── ...
```

The architecture strictly ensures that all spatial mathematics operate locally and securely on safe, minimal memory footprints. The preflight module will be invoked by the FastAPI endpoint immediately after successful semantic compilation. It will execute a series of lightweight, synchronous checks against the `WorkflowConfig` payload. Crucially, the preflight module must execute a "run 0" sequence, which involves a single initialization step without advancing the molecular dynamics timestep. This relies on static analysis of the configuration and the initial `ase.Atoms` object to predict potential failures mathematically before they occur.

The architectural flow designates the `preflight.py` module as an intermediary phase located precisely between the `api.routes.workflows.py` compilation endpoint and the `core.orchestrator.py` execution engine. Once the Semantic Compiler generates a valid `WorkflowConfig`, the FastAPI handler does not immediately return success to the React frontend. Instead, it passes the compiled configuration to the `PreflightManager` class. This manager orchestrates a suite of specialized diagnostic workers. The architecture demands a plugin-style design for these workers, ensuring that new validation checks can be added seamlessly in future updates. The primary workers defined in this cycle are the `StructuralValidator`, the `DependencyValidator`, and the `LammpsSyntaxValidator`.

The `StructuralValidator` operates purely in Python memory. Its primary responsibility is analyzing the `ase.Atoms` object for fundamental geometric flaws. The architecture specifically avoids calling any external C++ physics engines for this step to maximize speed. Instead, it relies on vectorized Numpy operations to calculate the pairwise distance matrix of the entire atomic system. This mathematical approach allows it to instantly identify overlapping coordinates or unphysical bond lengths (e.g., distances less than 0.5 Angstroms). Such flaws are critical because they generate near-infinite repulsive forces in empirical potentials, which would cause LAMMPS to exit immediately with a "Lost atoms" error, or cause Quantum ESPRESSO's SCF cycle to fail to converge. By catching these mathematically, the architecture prevents the heavy computational overhead of spinning up the external drivers. Furthermore, the `StructuralValidator` is responsible for checking periodic boundary conditions (PBC). It must verify that atoms are not placed exactly on the cell boundary in a way that violates the periodic image conventions, and that the total simulation box volume is sufficient to encompass the defined atomic positions without unphysical clipping.

The `DependencyValidator` performs synchronous file system and environment checks. Active learning workflows are heavily dependent on external assets. The architecture dictates that the `DependencyValidator` must verify the presence, read permissions, and basic formatting of required external assets. This includes Quantum ESPRESSO pseudopotential files (.UPF) for every unique chemical element present in the `ase.Atoms` object, pre-trained MACE foundation models (.model), and any user-provided reference datasets (.xyz files). The architecture also requires this validator to verify the execution environment itself. It must utilize Python's `shutil.which` to confirm the existence and execution permissions of external binaries such as `pw.x` (Quantum ESPRESSO), `pace_train` (the Pacemaker MLIP training executable), and `mpirun` (for parallel execution). If any of these dependencies are missing, the workflow is fundamentally incapable of running, and the architecture demands an immediate preflight rejection.

The most complex architectural component introduced in this cycle is the `LammpsSyntaxValidator`. While the Semantic Compiler (Cycle 02) is designed to generate syntactically correct LAMMPS commands, edge cases or complex user overrides from the GUI might introduce invalid syntax. To guarantee that the compiled LAMMPS script is flawless, the preflight architecture dictates that the system must spin up a lightweight, isolated instance of the LAMMPS Python library (`lammps`). It will feed the dynamically generated input string to this instance. Crucially, the architecture requires the script to be modified on-the-fly to append the `run 0` command, replacing any actual molecular dynamics `run N` commands. This `run 0` command forces LAMMPS to parse the entire script, initialize the simulation box, define the regions and groups, instantiate the interatomic potential (pair style and pair coeff), and perform a single thermodynamic evaluation without advancing the timestep.

If LAMMPS parses the script successfully and completes the zero-step initialization without raising a C++ exception, the system mathematically confirms the syntax is flawless and the combination of defined fixes and computes is physically compatible. If LAMMPS throws an error (e.g., an unrecognized fix style, an invalid parameter count, or an incompatible pair potential), the `LammpsSyntaxValidator` architecture dictates that the Python wrapper must catch the `LAMMPSException`. It must then extract the specific line number and the raw C++ error message, and translate it into a structured, user-friendly format. This isolation strategy is paramount; a LAMMPS syntax error must never be allowed to crash the main FastAPI server process. The architecture uses `try...except` blocks and potentially process isolation (via the `multiprocessing` module) to ensure the `LammpsSyntaxValidator` remains robust against severe segmentation faults occurring within the external library.

All of these diverse validators return their structured results to the central `PreflightManager`. The architecture dictates that this manager aggregates the findings into a comprehensive `DiagnosticReport` Pydantic model. The flow control mechanism depends entirely on the contents of this report. If the report contains any critical errors (e.g., missing executables, structural collisions, or LAMMPS syntax failures), the FastAPI endpoint returns an HTTP 400 Bad Request alongside the JSON serialized report. The React frontend consumes this report to highlight the specific DAG nodes or structural parameters that caused the failure, preventing the user from dispatching a doomed simulation. If the report is perfectly clean, or only contains non-critical warnings (e.g., a warning that the simulation box is slightly small but technically valid), the endpoint returns an HTTP 200 OK. This signals to the frontend that the configuration is safe, physically sound, and completely ready to be dispatched to the main active learning Orchestrator for execution. This architectural gatekeeper ensures the absolute stability of the PyAceMaker platform.

## Design Architecture
The `pyacemaker.core.preflight` houses the purely mathematical evaluation algorithms cleanly. This layer effectively transforms correctly ordered boundaries explicitly (e.g., minimum atomic distances) into robust validation boolean masks, precisely filtering invalid `WorkflowConfig` payloads cleanly.

A key domain invariant dictates strictly that the preflight property safely on the core instance must mathematically return exactly valid positive validation reports cleanly. The mapping algorithm translates these diagnostic structures precisely into matching React flow error messages seamlessly safely. The `DiagnosticReport` model will aggregate all errors, warnings, and informational messages generated during the preflight phase, ensuring that the frontend can display a comprehensive "health check" dashboard to the user.

The design of the preflight diagnostics must handle diverse failure modes. It must verify the structural integrity of the `ase.Atoms` object by checking for unphysically short interatomic distances (e.g., < 0.5 Angstroms), which indicate a bad initial geometry. It must confirm the existence of necessary executable paths (LAMMPS, PWscf) and the readability of any user-provided MACE models (.model files) or datasets. The architecture requires that these checks execute in under one second to maintain the responsiveness of the GUI, utilizing efficient Numpy operations to analyze atomic positions quickly. The diagnostic engine must be highly modular, allowing future developers to easily register new preflight checks as the framework evolves.

The core data structure introduced in this cycle is the `DiagnosticReport` Pydantic model. This model is explicitly designed to provide structured, programmatic feedback to the visual GUI, entirely replacing the traditional, error-prone method of asking users to read raw terminal output or parse log files. The `DiagnosticReport` contains three primary lists: `errors`, `warnings`, and `info`. Each list contains instances of a `DiagnosticMessage` sub-model. A `DiagnosticMessage` encapsulates the specific `node_id` where the issue originated (linking the error directly back to the visual DAG), a severity level enumeration, a human-readable description (e.g., "Atomic collision detected between Pt(4) and Pt(5)"), and a specifically actionable suggestion (e.g., "Check the initial structure geometry or run a preliminary relaxation using a classical potential").

The design strictly dictates that any message appended to the `errors` list immediately aborts the preflight process and flags the configuration as definitively invalid. Errors represent fundamental physical or systemic blockages. Examples include missing executables, syntax errors in the generated LAMMPS commands, or initial potential energies that evaluate to `NaN` (Not a Number) or infinity. The system cannot recover from these states.

Conversely, messages appended to the `warnings` list highlight suboptimal configurations that will technically run but might produce poor scientific results or exhibit reduced performance. For example, the `DependencyValidator` might issue a warning if the requested Quantum ESPRESSO pseudopotentials are from an older, deprecated library, or if the `StructuralValidator` detects that the simulation box size is unusually small for the number of atoms present, potentially leading to unphysical self-interaction artifacts across the periodic boundaries. Warnings do not block compilation; the system returns a 200 OK status, but the GUI displays a yellow alert icon to inform the user. The `info` list is reserved for successful validations, providing confirmation logs like "LAMMPS syntax verification passed successfully."

To achieve the mandated sub-second execution times for the `StructuralValidator`, the design leverages SciPy's `cKDTree` or Numpy's highly optimized `pdist` (pairwise distance) functions to calculate the distance matrix of the initial structure. A naive nested Python `for` loop would be catastrophically slow for systems containing tens of thousands of atoms, violating the responsiveness requirement of the web application. By vectorizing the distance calculation in C, the preflight module can instantly identify coordinate overlaps or unphysical bond lengths. Furthermore, the `LammpsSyntaxValidator` is designed to run in a protected `try...except` block, ensuring that even if the LAMMPS C++ core crashes due to a severe segmentation fault, the Python FastAPI server remains perfectly resilient, catching the crash and returning a controlled HTTP 500 Internal Server Error (or ideally, translating it into a `DiagnosticMessage` error) rather than bringing down the entire SaaS platform. This defensive design is critical for multi-tenant deployments.

## Implementation Approach
The implementation of the automated preflight diagnostics requires careful handling of atomic structures and system dependencies to ensure accurate predictions of runtime behavior without incurring significant overhead. The overarching strategy is to fail fast and fail loudly, translating deep physical errors into human-readable suggestions before any computational budget is burned. This requires a robust, plugin-based architecture for the various validation stages, ensuring each stage is highly cohesive and independently testable.

1.  **Establish Preflight Module:** Create the `preflight.py` inside the `src/pyacemaker/core/` directory. Define a central `PreflightManager` class. This manager will be instantiated with a compiled `WorkflowConfig` object. It will maintain a list of registered validator classes (e.g., `validators = [StructuralValidator(), DependencyValidator(), LammpsSyntaxValidator()]`). The manager will iterate through this list, invoking a standard `validate(config)` method on each instance. Create the `DiagnosticReport` and `DiagnosticMessage` Pydantic models within a `schema` subdirectory to standardize the output format, containing specific, strongly-typed lists for `errors` and `warnings` to guarantee the FastAPI JSON encoder correctly parses the response structure for the React frontend.
2.  **Define Structural Checks (Numpy Vectorization):** Implement the `StructuralValidator` class. The core implementation relies entirely on vectorized Numpy algorithms. Extract the `ase.Atoms` positions matrix (`atoms.get_positions()`). Utilize `scipy.spatial.distance.pdist` to calculate the condensed pairwise distance matrix. If the minimum distance falls below a pre-defined, physically impossible threshold (e.g., 0.5 Angstroms for standard metals), find the specific indices of the offending atoms using `scipy.spatial.distance.squareform` and `np.where`. Append a severe structural error to the `DiagnosticReport` detailing the exact indices involved. This mathematical implementation completely avoids slow Python `for` loops, ensuring the check executes in milliseconds even for structures containing 50,000+ atoms. Additionally, implement checks for the cell volume relative to the number of atoms to issue warnings if the density is unphysically high, signaling a potential coordinate scaling error during file import.
3.  **Implement Dependency Validation (Environment Introspection):** Create the `DependencyValidator` class within the preflight module. This implementation heavily utilizes Python's standard library to introspect the host environment. Utilize `shutil.which()` to verify that explicitly required external commands (e.g., `pw.x` for Quantum ESPRESSO, `pace_train` for MLIP generation, `mpirun` for parallel execution) are accessible in the system PATH and have execution permissions. Extract the paths for required input files—specifically pseudopotentials (`.UPF`) mapped to the elements in the structure, active learning reference datasets, and pre-trained MACE foundation models—from the `WorkflowConfig`. Utilize `os.path.exists()` and `os.access(path, os.R_OK)` to ensure these files exist and are readable by the PyAceMaker process. If any path is invalid, generate a specific `DiagnosticMessage` error, completely halting the workflow.
4.  **Implement LAMMPS Run 0 Validation (Subprocess Isolation):** Create the highly sensitive `LammpsSyntaxValidator` class. This implementation is complex because LAMMPS C++ exceptions can easily crash the hosting Python interpreter with a Segmentation Fault if not handled correctly. Do not use the direct `lammps` python module in the main thread. Instead, implement this validator by spawning a lightweight, isolated subprocess using `subprocess.run()` or `multiprocessing.Process`. Write a temporary python script that imports `lammps`, loads the generated LAMMPS string from the `WorkflowConfig`, appends a forced `run 0` command, and attempts initialization. The validator must capture `stdout` and `stderr`. If the subprocess returns a non-zero exit code, parse the `stderr` string to extract the specific `LAMMPS ERROR` line (e.g., "Unknown fix style"). This robust subprocess isolation guarantees that a syntax error or a bug in the LAMMPS compiled binary will never crash the FastAPI gateway server, translating the fatal C++ crash into a safely managed `DiagnosticMessage` error within the Python `DiagnosticReport`.
5.  **Refine API Integration (FastAPI Middleware):** Modify the `POST /api/v1/intent/compile` endpoint in `api/routes/workflows.py` to seamlessly integrate the preflight stage. Immediately after the Semantic Compiler generates the `WorkflowConfig`, instantiate the `PreflightManager` and invoke its validation suite. If the returned `DiagnosticReport` contains one or more entries in the `errors` list, immediately halt processing and return an HTTP 400 Bad Request. The response body must serialize the full `DiagnosticReport`, allowing the React frontend to iterate over the errors and visually highlight the problematic DAG nodes on the canvas. If the report contains only warnings or info messages, return an HTTP 200 OK along with the report, allowing the frontend to display yellow warning icons but permitting the user to dispatch the simulation.
6.  **Type Validation and Extensibility:** Ensure the entire `preflight.py` module uses strict Python 3.11+ type hints. The `validate` method signature of every validator plugin must explicitly type the incoming `WorkflowConfig` and the outgoing `DiagnosticReport`. This strict typing guarantees that the `PreflightManager` receives exactly the structure it expects, enabling confident JSON serialization. Design the module using a standard Interface or Abstract Base Class for the validators, allowing future developers to easily register new, highly specific preflight checks (e.g., a `MaceMemoryValidator` that statically analyzes the `.model` file size against available GPU VRAM) without modifying the core preflight orchestrator logic, ensuring long-term maintainability.

## Test Strategy
The testing isolates the purely mathematical functional evaluation successfully. The strategy focuses comprehensively on verifying that the diagnostic checks behave correctly across diverse invalid configurations and that edge cases do not cause false positives or crash the FastAPI server. The strategy must guarantee that the preflight acts as an impenetrable shield against bad configurations, verifying the mathematical algorithms and the subprocess isolation boundaries.

**Unit Testing Approach:**
Extensively rigorously test the independent `preflight.py` module inside `tests/unit/test_preflight.py`. The suite must achieve 100% branch coverage on the validation classes. We will begin with the `StructuralValidator`. We will inject manually created `ase.Atoms` instances with intentional, mathematically precise errors. For example, we will construct a system where two atoms share identical coordinates (distance = 0.0) and assert that the returned `DiagnosticReport` perfectly identifies the structural violation cleanly, including the correct atomic indices (e.g., "Collision between index 0 and 1"). We will construct another system where the atoms are 0.1 Angstroms apart, which is unphysical but non-zero, asserting that the vectorized Numpy distance threshold logic correctly flags the error. We will also explicitly test a pristine, relaxed crystal structure (e.g., FCC Copper), asserting that the validator returns an empty error list in milliseconds, confirming zero false positives for valid inputs.

Next, we will rigorously test the `DependencyValidator` in isolation using the `unittest.mock.patch` library. We will write parameterized tests verifying that missing file paths correctly trigger dependency errors. We will mock the `os.path.exists` function to return `False` for a specific Quantum ESPRESSO pseudopotential file path (e.g., `/tmp/fake_pseudo.UPF`) parsed from a dummy `WorkflowConfig`, asserting that the resulting `DiagnosticMessage` clearly instructs the user that the UPF file for a specific element is missing. We will also mock `shutil.which` to return `None`, simulating an environment where `pw.x` or `mpirun` is not installed, asserting the preflight catches the missing executable and flags it as a critical error.

The most critical unit tests will target the `LammpsSyntaxValidator`. Because this validator uses subprocess isolation, we must test its ability to handle hostile C++ outputs. We will mock the `subprocess.run` function. We will inject a `WorkflowConfig` containing a deliberately malformed LAMMPS command (e.g., `fix 1 all nve_typo`). We will configure the `subprocess.run` mock to return a `CompletedProcess` with `returncode=1` and `stderr="ERROR: Unknown fix style nve_typo (src/modify.cpp:123)"`. The unit test must explicitly assert that the validator successfully parses this standard error string, extracts the human-readable portion ("Unknown fix style nve_typo"), entirely prevents the Python process from raising a generic system exception, and correctly appends an error to the `DiagnosticReport` detailing the syntax failure. We will also test a pristine `WorkflowConfig` with valid LAMMPS syntax, mocking `returncode=0`, to ensure it returns an empty error list, signaling a successful preflight dry-run.

**Integration Testing Approach:**
Within `tests/integration/test_orchestrator.py` or `tests/integration/test_api_endpoints.py`, update the API tests to thoroughly verify that the full workflow mathematically generates safely explicit valid JSON configurations correctly and subjects them to the preflight gatekeeper. We will utilize the `httpx.AsyncClient` or the FastAPI `TestClient` to submit multiple diverse `IntentRequest` payloads to the compilation endpoint: one perfectly valid, one with a deliberate structural collision, and one deliberately designed to fail preflight by specifying a non-existent MACE model path in the advanced settings.

The integration test will then inspect the returned HTTP responses. It will explicitly assert that the valid payload returns an HTTP 200 OK with the compiled configuration and a clean diagnostic report containing zero errors. For the invalid payloads, it will assert that the endpoint correctly intercepts the preflight failure and returns an HTTP 400 Bad Request. The test will deeply inspect the JSON response body, ensuring it contains the detailed `DiagnosticReport` highlighting the specific missing file error or structural collision.

Finally, the integration test will execute a true end-to-end preflight using the actual (unmocked) `LammpsSyntaxValidator` on a tiny, computationally trivial system (e.g., 2 atoms of Argon). It will send an intent payload that generates a valid script, asserting that the real LAMMPS C++ engine executes the `run 0` initialization successfully within the API request lifecycle (taking less than one second) and returns a 200 OK. It will then send an intent payload that forces a syntax error, asserting that the real LAMMPS engine throws an exception that is successfully caught by the subprocess wrapper and transformed into a 400 Bad Request. This proves that the preflight diagnostics correctly act as a robust gatekeeper, preventing physically impossible or syntactically flawed configurations from proceeding to the execution phase in a realistic production environment, directly validating the architectural goals of Cycle 06.
