# Cycle 03: Spatial Tagging and ASE Integration - UAT

## Test Scenarios
The primary user acceptance testing scenarios focus specifically on proving the absolute robustness and flawless mathematical translation of the visual bounding-box representations generated by the React Flow/Three.js frontend. They also verify their precise integration seamlessly into the highly specific, text-based atomic tagging mechanisms native to LAMMPS. The UAT simulates the safe mathematical processing of a simplified spatial GUI representation perfectly. This cycle proves that user-drawn regions on the screen reliably become physical constraints in the simulation, abstracting away complex geometry calculations.

* **SCENARIO-03-A [Priority: High] - Successful Spatial Bounding Box Translation:** The UAT must simulate a user completing the explicit simplified spatial configuration. The interface successfully injects a fully valid mathematical precise JSON spatial bounding box payload directly (e.g., Z-min: 0.0, Z-max: 5.0, Action: "FREEZE") into the REST API. The API explicitly correctly compiles the entire spatial configuration accurately into the highly precise nested schema natively required. This demonstrates the core functionality of the visual tagging feature. The simulated user loads an FCC Platinum slab, which occupies a region from Z=0.0 to Z=20.0 Angstroms. They use the visual interface to "paint" the bottom three layers of the slab, defining a bounding box extending from Z=0.0 to Z=6.0 Angstroms, and setting the intent to "FREEZE". When they submit this payload, the backend API parses the `SpatialRegion` model, passes the coordinates to the `pyacemaker.utils.spatial` module, and applies a boolean mask identifying the specific atoms within the bottom layer. The Semantic Compiler assigns a unique integer tag (e.g., `1`) to these atoms and generates the corresponding `WorkflowConfig`. The test suite will meticulously inspect the final `WorkflowConfig` payload, verifying that it contains the explicit LAMMPS `region` and `group` definitions corresponding to the mathematical boundaries, and that a `fix setforce 0.0 0.0 0.0` command is appropriately applied to that specific atomic group. This proves the system correctly abstracted the visual painting into a physically rigorous molecular dynamics constraint. To further ensure robustness, the test will inject a bounding box that perfectly aligns with an atomic plane (e.g., at Z=6.0) and assert that the deterministic inclusive/exclusive logic correctly identifies whether those specific boundary atoms are included in the frozen group, proving the spatial mathematics are free from ambiguous floating-point rounding errors that could cause simulation inconsistencies across different hardware architectures.

* **SCENARIO-03-B [Priority: High] - Accurate Mathematical ASE Masking Generation and Conflict Resolution:** The UAT tests that complex internal vector mathematical logic correctly populates the correct intelligent Boolean masking arrays, and correctly handles contradictory visual inputs. The simulated user loads a metallic surface model and deliberately draws overlapping spatial regions using the UI. They draw one `SpatialRegion` (Z-min: 0.0, Z-max: 10.0) with an action of "FREEZE", and a second `SpatialRegion` (Z-min: 5.0, Z-max: 15.0) with an action of "THERMOSTAT". This creates a physically conflicting zone between Z=5.0 and Z=10.0 where atoms are instructed to be both rigidly fixed and actively thermalized. The frontend submits this conflicting payload to the `/api/v1/intent/compile` endpoint. The backend API must receive this payload and invoke the spatial module. The test suite will verify that the spatial module's deterministic conflict resolution algorithm executes correctly, resolving the ambiguity according to a predefined priority hierarchy (e.g., "FREEZE" overrides "THERMOSTAT"). The resulting `ase.Atoms` tags must reflect this resolution flawlessly, ensuring that atoms in the overlap zone receive only the tag corresponding to the "FREEZE" action. The generated LAMMPS script must accurately reflect these boundaries without producing contradictory physical commands, proving the system is robust against confusing or conflicting visual inputs. The test will also verify that if the priority hierarchy cannot resolve the conflict (e.g., two identical bounding boxes with different, mutually exclusive actions like `THERMOSTAT_1` and `THERMOSTAT_2` with different target temperatures), the module immediately raises a specific `ValueError` detailing the conflict, which the API gateway translates into a 400 Bad Request error returned to the frontend.

* **SCENARIO-03-C [Priority: Medium] - Handling of Empty Selections and Invalid Geometry:** The UAT will simulate a scenario where the user draws a bounding box in empty space (i.e., a region containing no atoms) or provides inverted coordinates. The system must gracefully process this input, identifying that zero atoms are selected, and compile the workflow without generating invalid LAMMPS commands (e.g., it should omit empty `group` definitions ) and without crashing the semantic compiler. In the first part of this scenario, the simulated user defines a `SpatialRegion` (Z-min: 100.0, Z-max: 110.0) that is outside the boundaries of the loaded atomic structure. The API successfully processes the payload, detects that the resulting boolean mask selects 0 atoms, and intelligently omits generating any LAMMPS `group` or `fix` commands for that empty region, preventing simulation crashes. In the second part, the simulated user attempts to submit a payload with inverted bounding box coordinates (e.g., Z-min: 15.0, Z-max: 5.0). The Pydantic schema validation layer must intercept this payload before it reaches the spatial mathematics module, immediately returning a 422 Unprocessable Entity error and a message explaining the geometric invalidity of the drawn bounding box, demonstrating robust input validation at the API boundary. Finally, the UAT will test a scenario where a user draws a region that perfectly encompasses the entire simulation cell, attempting to apply a constraint to every single atom. The test will verify that the system correctly identifies all atoms, generates the appropriate tags, but optimizes the generated LAMMPS script by utilizing the global `all` group instead of explicitly defining a redundant bounding box region, proving the compiler includes intelligent simplification logic to optimize the resulting molecular dynamics input scripts.

## Behavior Definitions
These behavior definitions map to the exact User Test Scenarios, specifically defining the deterministic Gherkin-style assertions expected from the PyAceMaker Spatial Tagging module. This provides a clear, executable specification for the spatial mathematics.

**Feature: Visual Spatial Bounding Box Configuration Semantic Compilation**

**Scenario 1: Flawless Translation of Bounding Box to Native Tagging Property**
**GIVEN** the PyAceMaker Spatial Tagging module is fully active and configured
**AND** the simulated GUI perfectly defines the node `SpatialRegion` seamlessly correctly with explicitly valid mathematical Z-axis boundaries
**WHEN** the simulated frontend explicitly sends a precise request passing through the `spatial.py`
**THEN** the Spatial Tagging API gateway responds immediately with a valid `ase.Atoms` instance
**AND** the compiled `tags` effectively natively accurately matches the original input spatial mathematical boundaries successfully, confirming correct atomic selection.

**Scenario 2: Secure Translation of Tagging Arrays into LAMMPS Fixes**
**GIVEN** the PyAceMaker Semantic Compiler module is fully active and configured
**AND** the user intentionally purely explicitly avoids manually configuring highly complex LAMMPS text commands
**WHEN** the simulated frontend explicitly sends a precise request
**THEN** the compiled rigorously nested `WorkflowConfig` effectively accurately automatically contains highly intelligent correct generated LAMMPS explicit text string commands (e.g., `fix 1 freeze_group setforce 0.0 0.0 0.0`).

**Scenario 3: Deterministic Resolution of Overlapping Spatial Regions**
**GIVEN** the PyAceMaker Spatial Tagging module is active
**AND** the user defines two distinct `SpatialRegion` boundaries that intersect physically
**AND** one region specifies a "FREEZE" action while the overlapping region specifies a "THERMOSTAT" action
**WHEN** the simulated frontend submits this payload to the compilation endpoint
**THEN** the spatial masking algorithm executes its deterministic conflict resolution logic
**AND** atoms within the intersection zone are assigned a single, definitive integer tag based on predefined action priorities
**AND** the resulting compiled `WorkflowConfig` contains physically consistent LAMMPS commands, ensuring no contradictory forces are applied to the overlapping atomic indices.

**Scenario 4: Graceful Handling of Empty Spatial Regions and Invalid Boundaries**
**GIVEN** the PyAceMaker Spatial Tagging module is active
**AND** the simulated user defines a `SpatialRegion` (e.g., Z-min: 100.0, Z-max: 110.0) that is outside the boundaries of the loaded atomic structure
**WHEN** the frontend submits the workflow payload for compilation
**THEN** the spatial masking algorithm evaluates the region and identifies 0 selected atoms
**AND** the API successfully returns a `WorkflowConfig`
**AND** the resulting configuration omits any unnecessary LAMMPS `group` or `fix` commands related to the empty region, preventing simulation crashes.
**WHEN** the user alternatively submits a payload with inverted Z boundaries (Z-min: 10.0, Z-max: 0.0)
**THEN** the API gateway immediately rejects the request with an HTTP 422 Unprocessable Entity status code before attempting any spatial calculations.
