# Cycle 01: Establish Foundation API and Schema Structure

## Summary
The primary objective of Cycle 01 is focused on establishing the fundamental, rigid architectural layer for the PyAceMaker visual GUI gateway, specifically ensuring absolute isolation between external API inputs and the internal Orchestrator execution logic. This critical phase meticulously introduces the FastAPI application scaffolding and deeply enforces strict `pydantic`-based schemas designed to model the Intent-Driven requests mandated by the new "Core Philosophy". This cycle lays the precise foundation necessary for the abstract translation of high-level graphical concepts—such as the Accuracy vs. Speed sliders—into executable physical configurations later.

Crucially, the introduction of this API layer is purely additive. It ensures the safety of the current `src/pyacemaker/core` engine by not modifying any of its state logic. The new components depend entirely on strict validation checks enforcing `extra="forbid"` and rigorous type-casting rules. This creates a robust Anti-Corruption Layer (ACL), mathematically guaranteeing that malformed JSON payloads originating from the frontend or malicious actors cannot penetrate the core domain state machine. Furthermore, we implement secure environment variables and precise Cross-Origin Resource Sharing (CORS) configurations perfectly aligned with a scalable Software as a Service (SaaS) architecture. The completion of this cycle strongly proves the capability to strictly receive, instantly validate, and correctly process complex, semantically abstract Direct Acyclic Graph (DAG) inputs safely via HTTP endpoints, setting the stage for the translation compilation logic in Cycle 02. We adhere to the AC-CDD methodology, separating routing logic from domain models perfectly.

The value delivered in Cycle 01 forms the bedrock of the entire Intent-Driven GUI platform. Without this strict validation layer, the system would remain vulnerable to configuration injection and unexpected runtime failures, negating the benefits of a user-friendly frontend. This phase ensures that the foundation is solid, secure, and ready for advanced feature integration in the subsequent development cycles. The implementation here sets the rigorous standards for all APIs that will follow, establishing patterns for exception handling, dependency injection, and asynchronous request processing. By successfully concluding Cycle 01, we provide a mathematically guaranteed safe entry point for the visual workflow editor, effectively bridging the gap between a web-based client and a highly sensitive Python simulation environment. This is achieved without introducing brittle mock objects into the production codebase, relying instead on pure functional validation at the network boundary.

A critical addition in this foundational cycle is the introduction of a Job Management abstraction. A FastAPI server cannot safely hold a synchronous HTTP connection open for days while a molecular dynamics simulation runs. Therefore, the system must be designed from the ground up to return a unique Job UUID immediately upon successfully accepting an execution intent, delegating the actual compilation and simulation to asynchronous background workers. This Job UUID becomes the primary routing key for all subsequent interactions, including real-time WebSocket telemetry defined in Cycle 04.

## System Architecture
The implementation aligns exactly with the master PyAceMaker system architecture, isolating external routing concerns from the physics execution logic. We introduce the `pyacemaker.api` subsystem designed to act as the primary asynchronous interface. This layer comprises the `FastAPI` instance, structured routing files (e.g., `routes/workflows.py` and `routes/jobs.py`), and robust dependency injection mechanisms designed for database and state manager interactions. Simultaneously, we meticulously extend the existing domain modeling paradigm by establishing the critical `pyacemaker.domain_models.gui_schema` module. This module encapsulates the `Pydantic` models describing the user's intent. The architectural boundary dictates that the `api` module can strictly read `gui_schema`, but `gui_schema` must remain free of any HTTP or routing logic, maintaining clean domain boundaries.

```text
src/pyacemaker/
├── api/                       # [NEW] Highly Secure FastAPI Application Boundary
│   ├── routes/                # [NEW] REST endpoints for the Visual Platform
│   │   ├── __init__.py
│   │   ├── workflows.py       # [NEW] Endpoint explicitly receiving DAG/Intent JSON payloads
│   │   └── jobs.py            # [NEW] Endpoint managing execution state and returning Job UUIDs
│   ├── dependencies.py        # [NEW] Injection mechanisms for DB and Orchestrator state
│   └── server.py              # [NEW] Uvicorn execution entrypoint and CORS configuration
├── core/
│   └── ...                    # [EXISTING] Untouched core state logic
├── domain_models/
│   ├── config.py              # [EXISTING]
│   ├── gui_schema.py          # [NEW] Extremely strict Intent-Driven Pydantic payloads
│   └── ...
└── main.py                    # [MODIFIED] Additive CLI command launching the API
```

The FastAPI instance operates utilizing asynchronous methodologies (`async def`), specifically allowing the highly concurrent processing of multiple configuration validation requests without blocking the event loop. The `gui_schema.py` explicitly leverages nested `BaseModel` structures, enforcing constraints utilizing the `Field` parameter to constrain scalar values, such as ensuring the `accuracy_speed_slider` is mathematically bounded between `1` and `10`. This asynchronous foundation is vital for supporting real-time visual feedback and maintaining a highly responsive user experience, especially when dealing with computationally expensive molecular dynamics calculations in the backend.

The architecture guarantees that any failure in validation immediately rejects the request with a detailed 422 Unprocessable Entity error, providing immediate feedback to the React frontend. This prevents resource starvation and ensures that only clean, well-formed intent parameters ever reach the Semantic Compiler in the next architectural tier. The `api` module acts as a strict firewall. It is designed such that the core molecular dynamics execution engine is completely unaware of its existence. The orchestrator does not know whether it was invoked via a YAML file from the command line or via a JSON payload from the React frontend. This abstraction is paramount. By enforcing this isolation, we ensure that the highly complex logic developed in previous iterations of PyAceMaker—including the Master-Slave LAMMPS resumption algorithms and the MACE incremental training pipelines—remains untouched and safe from unintended side effects.

Furthermore, the design of the FastAPI application boundary incorporates scalable principles suitable for cloud deployment. The `server.py` file configures the Uvicorn ASGI server with specific worker limits and connection timeouts to prevent denial-of-service scenarios. It also establishes the CORS policy, which is essential because the React frontend will typically be served from a different origin port (e.g., localhost:3000) than the Python backend (e.g., localhost:8000). The `dependencies.py` file introduces a clean mechanism for dependency injection, allowing the API routes to acquire database sessions or mock objects safely. This injection pattern is particularly critical for testing, as it allows us to swap out the real PyAceMaker orchestrator for a lightweight dummy orchestrator during unit tests, ensuring that the API layer can be verified without requiring a full installation of LAMMPS or Quantum ESPRESSO.

The `workflows.py` routing module is designed to be versioned (e.g., `/api/v1/intent/compile`). This versioning strategy protects the frontend against breaking changes in the future. As the Intent-Driven GUI evolves and new visual nodes are added, we can introduce a `v2` router while maintaining backward compatibility for older frontend deployments. The primary endpoint developed in this cycle will solely focus on receiving the DAG payload and returning a structured response indicating successful validation or detailed error paths. It does not yet perform the translation into physical `WorkflowConfig` schemas, reserving that complex logic exclusively for Cycle 02. This separation of validation and compilation strictly adheres to the Single Responsibility Principle.

The domain model implementation in `gui_schema.py` is the most critical aspect of the system architecture for this cycle. The models defined here act as the definitive contract between the React developers and the backend Python engineers. Any change to these models must be heavily scrutinized. The schema will define the base structure of a node in the Directed Acyclic Graph (DAG), including necessary geometric coordinates for visual placement on the canvas, even though these coordinates are irrelevant to the physics simulation. This ensures the backend can act as a persistent state manager for the frontend, allowing users to save their visual workflows and reload them later exactly as they were drawn. The strictness of the Pydantic models ensures that no strings containing shell injection vectors (e.g., backticks or semicolons) can be passed into fields that will eventually be compiled into system calls or LAMMPS input scripts. This architectural decision fundamentally secures the application at the very boundary of interaction.

## Design Architecture
The design architecture of this initial phase revolves specifically around the implementation of the `pyacemaker.domain_models.gui_schema` models. These schemas dictate the exact API contract and are designed strictly adhering to the Intent-Driven abstraction paradigm. The fundamental design philosophy is to restrict the configuration space explicitly to prevent the user from making mathematically or physically unsound choices. We achieve this by heavily leveraging the robust data validation capabilities of Pydantic V2, ensuring that all incoming data is strongly typed before it ever enters a Python function.

The primary domain concept introduced is the `IntentRequest`. This model heavily abstracts complex active learning configurations into incredibly simple, user-friendly parameters. The exact invariant here dictates that complex variables like `candidate_threshold`, `lammps_command_string`, or `pace_train_batch_size` must be explicitly excluded from this schema, physically preventing the user from bypassing the compiler. By restricting the user input to pure intent (e.g., material target, desired speed), we eliminate the cognitive burden of hyperparameter tuning. The `IntentRequest` model is the root of the hierarchy and serves as the single entry point for all incoming configuration payloads.

Within the `IntentRequest`, the `DagNode` schema represents the structural components of the visual workflow editor. Key invariants dictate that every `DagNode` must possess a valid structural UUID and an explicitly enumerated type. We will define an `Enum` class named `NodeType`, containing strict definitions such as `INITIAL_STRUCTURE`, `MACE_TRAINING`, `ACTIVE_LEARNING_LOOP`, and `EON_TRANSITION_SEARCH`. By using enumerations, we ensure that the frontend cannot invent new, unsupported node types. Constraints strictly demand that node connections form a valid Directed Acyclic Graph (DAG), ensuring no infinite loops are created in the logical workflow pipeline. The schema will use Pydantic validators to trace the edges of the provided nodes and assert that the graph is indeed acyclic before accepting the payload.

The schemas specify `model_config = ConfigDict(extra="forbid", strict=True)`. This ensures absolute backward compatibility and security by rejecting any unexpected fields, maintaining the absolute integrity of the payload. The data produced by this layer acts as the explicit input for the `WorkflowCompiler` (developed in Cycle 02). This rigorous data modelling is the cornerstone of the PyAceMaker platform, guaranteeing that the visual frontend cannot introduce subtle, hard-to-debug errors into the core molecular dynamics execution loop. The design explicitly favours compile-time safety and strict runtime validation over flexible, but dangerous, dynamic typing.

Furthermore, the design includes specialized sub-models for the specific data required by each `NodeType`. For example, an `INITIAL_STRUCTURE` node must include data detailing the initial atomic configuration. Instead of accepting arbitrary text, the schema will define an `InitialStructureData` model that strictly requires a base64 encoded string of an XYZ or POSCAR file, or a specific chemical formula and lattice parameters if the system is to be generated procedurally. This level of granularity ensures that when the payload finally reaches the Semantic Compiler in Cycle 02, the compiler is guaranteed to have the exact structural data required to initialize the `ase.Atoms` objects. The design architecture of Cycle 01 is thus a deliberate exercise in constraint definition, prioritizing absolute system stability and strict domain boundaries above all other concerns. This rigorous approach prevents the classic "garbage in, garbage out" problem that plagues many scientific software interfaces.

## Implementation Approach
The implementation of the foundational API and schema structure will proceed through a series of methodical, carefully ordered steps. This sequential approach ensures that each layer is fully tested and robust before the next layer is added, minimizing integration risk. We will employ Test-Driven Development (TDD) principles throughout this process, writing failing tests for the schemas and endpoints before implementing the actual logic.

1.  **Define GUI Schemas:** Begin by strictly implementing the `gui_schema.py` module within the `domain_models` directory. Construct the `NodeType` enumeration and the base `DagNode` Pydantic model. Then, implement the specific data models for each node type (e.g., `InitialStructureData`, `ActiveLearningData`). Construct the root `IntentRequest` model. Utilize `pydantic.Field` to enforce bounds on integer parameters (e.g., `ge=1`, `le=10` for the accuracy slider). Apply `extra="forbid"` and `strict=True` to the `ConfigDict` on all models to rigorously prevent payload injection and ensure absolute type safety. Implement a `@model_validator` to check that the list of nodes provided forms a valid DAG structure. This validator must implement a topological sort algorithm (e.g., Kahn's algorithm) within the Pydantic class method to mathematically detect cycles across the user-provided array of edges. If a cycle is found, it must raise a specific `ValueError` detailing the nodes involved in the infinite loop. This complex validation happens entirely within the Pydantic model, isolating the graph logic from the FastAPI routing functions.
2.  **Initialize FastAPI Application:** Create the `api/server.py` module housing the `FastAPI` instance. Strictly configure comprehensive CORS middleware permitting cross-origin requests specifically designed for a highly decoupled React application running on a separate port during development (e.g., explicitly allowing origins like `http://localhost:3000` via the `CORSMiddleware`). Ensure the application initializes cleanly, sets up basic Python standard logging to integrate seamlessly with the existing PyAceMaker logger, and registers standard exception handlers for validation errors. Include an explicit `/health` endpoint that simply returns `{"status": "ok"}` to allow container orchestrators like Kubernetes or Docker Swarm to monitor the API's status and automatically restart failed uvicorn workers.
3.  **Implement REST Endpoints and Job Routing:** Construct the `api/routes/workflows.py` and `api/routes/jobs.py` routing modules. Define an asynchronous `POST /api/v1/intent/compile` endpoint utilizing the `IntentRequest` class directly as the input payload parameter in the Python function signature, allowing FastAPI's internal dependency injection to handle the complex Pydantic JSON unmarshalling and validation automatically. The endpoint must return a simplified JSON success response (e.g., `{"status": "success", "message": "Payload validated successfully", "node_count": len(payload.nodes)}`) confirming the payload was received. Crucially, implement a `POST /api/v1/jobs/submit` endpoint. This endpoint accepts the intent payload, immediately generates a unique UUID `job_id`, and returns it to the client with a 202 Accepted status. The actual processing of this job is deferred to background tasks. Ensure the endpoints use `async def` to maintain high concurrency.
4.  **Establish Dependency Injection:** Construct the `api/dependencies.py` module providing asynchronous generator functions designed to safely supply secure database sessions or mock Orchestrator instances for the initial validation pathways. This is crucial for maintaining testability and avoiding tight coupling to the physical execution drivers. It allows the API to function in absolute isolation during CI/CD pipelines. For example, implement a `get_db_session()` dependency that yields a scoped SQLAlchemy session if the system uses a database to store past workflow runs, ensuring the session is explicitly closed in a `finally` block after the endpoint returns.
5.  **Integrate CLI Entrypoint:** Modify the existing `src/pyacemaker/main.py` CLI logic to gracefully accommodate the new GUI platform alongside the legacy script-based workflows. Add a new sub-command (e.g., `pyacemaker gui --port 8000`) designed to cleanly bootstrap the Uvicorn server utilizing the new `server.py` application definition. Use Python's `argparse.ArgumentParser` sub-parsers to handle the specific arguments for the GUI server (like `--host` and `--workers`). Ensure this completely isolates the web server logic and does not break the existing command-line execution pathways for legacy script users who still rely exclusively on `pyacemaker --config config.yaml` to run physics simulations.
6.  **Refine Error Handling:** Implement custom exception handlers within the `server.py` module to capture Pydantic `ValidationError` instances and translate them into user-friendly JSON responses formatted specifically for the React frontend's consumption. This ensures the frontend receives highly actionable, granular feedback when a user submits an invalid configuration, pointing them exactly to the problematic field (e.g., returning a structured array of error objects specifying the exact nested dictionary path like `nodes.0.data.accuracy_slider` and translating the cryptic Pydantic error into a clear string like "Accuracy slider must be between 1 and 10"). This custom handler is essential to prevent the default FastAPI error format from leaking internal Python server details or raw stack traces directly to the client browser.

## Test Strategy
The testing methodology for this cycle explicitly isolates the API and validation layers perfectly from the complex core physical execution algorithms. This ensures fast test execution and pinpoints errors directly within the new schema definitions or routing logic, adhering to the principles of unit isolation. The tests must be capable of running independently without requiring LAMMPS or Quantum ESPRESSO to be installed on the host system. The entire suite for this cycle should execute in under one second.

**Unit Testing Approach:**
We mandate precise, exhaustive validation focused solely on the Pydantic schemas within a dedicated `tests/unit/test_gui_schema.py` file. The test suite will construct rigorous assertions actively injecting intentionally malformed JSON payloads. Test cases must include injecting floating-point values where integers are expected for the accuracy slider (asserting strict type coercion failures), out-of-bounds inputs (e.g., 0 or 11), and highly nested arbitrary key-value injections (e.g., `{"sneaky_injection": "rm -rf /"}`) to explicitly prove the `extra="forbid"` configuration is active and impenetrable. The tests will assert that precise `ValidationError` exceptions are raised cleanly, verifying the specific error message matches the constraint violated (e.g., asserting "Input should be less than or equal to 10").

We will specifically test the `DagNode` validation, ensuring that required fields like `id` and `type` are strictly enforced and that invalid strings provided for enumerations (e.g., `type="MAGIC_NODE"`) are immediately rejected. A significant portion of the unit tests will focus on the complex `@model_validator` responsible for ensuring the DAG structure is acyclic. We will construct programmatic mock payloads representing valid linear workflows (Node A -> Node B -> Node C), complex valid branched workflows (Node A -> Node B, Node A -> Node C), and explicitly invalid cyclical workflows (e.g., Node A points to Node B, which points back to Node A), asserting that the cyclical configurations immediately trigger a Pydantic validation failure. This unit testing forms the first line of defense against configuration drift and ensures the Anti-Corruption Layer functions exactly as designed. Furthermore, we will test the base64 decoding logic within the `InitialStructureData` model to ensure it gracefully handles corrupted, incomplete, or non-base64 strings without crashing the Python process, catching the `binascii.Error` and converting it to a schema validation error.

**Integration Testing Approach:**
We will construct deep integration tests utilizing `httpx.AsyncClient` within `tests/integration/test_api_endpoints.py`. These tests will spin up the complete asynchronous FastAPI instance entirely inside memory using the `TestClient`, completely avoiding network overhead and ensuring deterministic test execution that doesn't conflict with other running services. We will dispatch fully formed, perfectly validated JSON `POST` requests directly to the `/api/v1/intent/compile` endpoint. The tests will assert that the application returns HTTP 200 OK statuses and the correct JSON success messages (e.g., verifying the returned `node_count` precisely matches the number of nodes in the input payload). We will also test the `/api/v1/jobs/submit` endpoint, asserting that it successfully returns a 202 Accepted status containing a valid UUID-v4 format `job_id` string, proving the robust functionality of the entire routing and payload unmarshalling architecture from end-to-end.

Furthermore, integration tests will explicitly simulate malicious endpoint requests to ensure the gateway degrades gracefully and maintains system stability under active duress. This includes testing extremely large JSON payloads (e.g., injecting a 50MB string into a single node ID field) to verify that FastAPI's internal ASGI request size limits successfully prevent memory exhaustion. We will test sending payloads with missing authentication headers (if authentication middleware is implemented) to verify proper HTTP 401 Unauthorized responses are generated before the payload is even parsed. Finally, we will send completely arbitrary, malformed text strings (non-JSON data) to the endpoint to ensure the server responds safely with a 422 Unprocessable Entity or 400 Bad Request, rather than crashing the worker with a 500 Internal Server Error when the built-in JSON parser fails to decode the bytes. This guarantees the API is robust enough for production deployment on public-facing internet infrastructure, safely protecting the sensitive PyAceMaker active learning orchestrator residing behind it from any network-level anomalies.
