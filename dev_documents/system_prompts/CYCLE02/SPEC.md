# Cycle 02: Semantic Compiler and Config Translation

## Summary
The primary objective of Cycle 02 focuses specifically on bridging the enormous structural gap between the abstract, user-friendly `gui_schema.py` representations defined in Cycle 01 and the highly complex, technically dense `WorkflowConfig` structures required by the PyAceMaker execution orchestrator. This phase is dedicated to the meticulously engineered implementation of the `pyacemaker.domain_models.compiler` module. The Semantic Compiler effectively functions as the intelligent core of the Intent-Driven GUI platform, mathematically transforming highly abstract visual concepts—like a React Flow Directed Acyclic Graph (DAG) representing "Initial Structure -> Fine-Tuning -> Active Learning"—into a fully rigorously validated YAML-equivalent configuration natively understandable by the core Python engine.

Crucially, this compiler layer explicitly guarantees that backward compatibility is maintained. It acts purely as an intelligent, programmatic configuration generator, carefully injecting intelligent default thresholds isolating the non-expert engineer from the mathematical intricacies of LAMMPS configurations and MACE active learning loop interval optimization. By completing Cycle 02, the API gateway can natively accept arbitrary user intent and securely translate it for subsequent execution. This process significantly reduces the cognitive load on researchers, allowing them to focus on materials design rather than script debugging. Without this translation layer, the visual interface would simply be a generic drawing tool; with it, the interface becomes a powerful, domain-specific integrated development environment for computational materials science.

The Semantic Compiler is designed to be fully deterministic and strictly pure functional. It does not perform any I/O operations, database lookups, or system calls. This purity ensures that the translation process is lightning fast, infinitely scalable, and trivially testable across thousands of edge cases without ever requiring a running molecular dynamics engine. This cycle delivers the intelligence required to make the visual frontend a reality, cementing the bridge between human intent and machine execution. The Semantic Compiler is the definitive component that transforms PyAceMaker from a powerful, but difficult-to-use, developer tool into an accessible, mass-market scientific instrument. It embodies the principle of "smart defaults," ensuring that a user only needs to specify what they want to achieve, leaving the "how" entirely to the software.

## System Architecture
The implementation aligns with the PyAceMaker additive architecture. It introduces the independent `compiler` translation layer positioned cleanly between the API routing and the core engine configuration layer. The `pyacemaker.domain_models.compiler` acts as a pure functional mathematical layer strictly consuming `gui_schema.IntentRequest` and outputting instances of `pyacemaker.domain_models.config.WorkflowConfig`.

```text
src/pyacemaker/
├── api/                       # [EXISTING]
│   ├── routes/                # [MODIFIED] Route utilizes compiler
│   │   ├── ...
│   │   └── workflows.py       # [MODIFIED] Integrates compiler module perfectly
│   └── ...
├── domain_models/
│   ├── config.py              # [EXISTING] Untouched core state logic
│   ├── gui_schema.py          # [EXISTING]
│   └── compiler.py            # [NEW] Purely mathematical translation functional mapping
└── ...
```

The architecture strictly enforces that the compiler function operates without any side effects. It performs absolutely zero I/O operations and never interacts strictly with the physical execution environment, preserving complete perfect testability. This separation of concerns is fundamental to the AC-CDD methodology, ensuring that the translation logic can evolve independently of the underlying execution drivers. Should the structure of the `WorkflowConfig` change in the future, only the `compiler.py` module needs updating, shielding the frontend API from cascading failures. This isolation is critical for maintaining a stable API surface area while allowing the internal physics engines to upgrade their parameters (e.g., adding new LAMMPS fix styles or changing Quantum ESPRESSO convergence algorithms) without breaking the client-facing endpoints.

The `compiler.py` module is constructed as a stateless transformer. It receives a directed graph of visual nodes (represented by the `IntentRequest` object) and recursively traverses this graph to construct the linear, deeply nested state machine representation (`LoopStrategy`) expected by the PyAceMaker core engine. This topological sort is the first critical step in the architecture. The visual GUI inherently allows users to construct non-linear structures—for example, a single initial structure branching into two parallel active learning loops. The Semantic Compiler architecture must either mathematically flatten these branches into a sequential workflow (if supported by the core engine) or gracefully reject unsupported topologies with a highly specific `CompilerError` indicating the structural incompatibility.

Once the topological order is established, the architecture utilizes a Factory Pattern implementation. For each node type defined in the `gui_schema.NodeType` enumeration, the compiler instantiates a specific, isolated sub-compiler function (e.g., `_compile_initial_structure_node()`, `_compile_active_learning_node()`). This pattern ensures that the massive complexity of translating the entire workflow is broken down into small, highly cohesive, and independently testable units. Each sub-compiler is responsible for injecting the necessary intelligent defaults relevant to its specific domain. For instance, the MACE training sub-compiler inherently knows the optimal default batch sizes and learning rate schedulers for the current generation of the foundation model, shielding the user from these moving targets.

Furthermore, the architecture demands that the final output of the compiler is not merely a dictionary, but a fully instantiated and validated instance of the core `pyacemaker.domain_models.config.WorkflowConfig` Pydantic model. This means the compiler itself relies on the core engine's existing robust validation logic as a final sanity check. If the Semantic Compiler contains a bug and accidentally generates an invalid physical parameter (e.g., a negative temperature for a Langevin thermostat or an unrecognized chemical symbol for a pseudopotential mapping), the instantiation of the `WorkflowConfig` will fail. This failure will raise a `ValidationError` inside the compiler, which is then caught and translated into a `CompilerError` that immediately bubbles up to the FastAPI endpoint, preventing the flawed configuration from ever reaching the execution orchestrator. This "double-validation" strategy—first validating the visual intent at the API boundary, and then validating the compiled physics payload—is the architectural keystone that guarantees absolute system stability under all circumstances. It ensures that the system is fail-safe; a bad compilation cannot result in a bad simulation.

Finally, the Semantic Compiler architecture must handle the translation of the abstract "Accuracy vs. Speed" slider. While the exact mathematical heuristics for this translation are deferred to Cycle 05, the architecture established in Cycle 02 must provide the integration points for these heuristics. The compiler must intercept the slider value from the `IntentRequest` and route it through a placeholder scaling function before injecting the resulting hyperparameters into the `ActiveLearningLoop` configurations (e.g., modifying the `candidate_threshold` of the Two-Tier Evaluator or the `n_steps` of the Lammps molecular dynamics loop). This forward-looking design ensures that subsequent development cycles can plug their sophisticated algorithms directly into the established compilation pipeline without requiring major architectural refactoring. The Semantic Compiler is essentially the intelligent heart of the GUI platform, mediating all communication between the user's intent and the physical reality of the simulation, translating "fast simulation of Platinum" into thousands of lines of precise, executable Python and C++ instructions.

## Design Architecture
The `pyacemaker.domain_models.compiler` houses the functional mapping algorithms. This layer mathematically transforms the `DagNode` sequence explicitly into sequentially ordered `pyacemaker.domain_models.config.LoopStrategy` lists cleanly. The design prioritizes immutability; the compiler takes a read-only view of the `IntentRequest` and returns a newly constructed `WorkflowConfig` without modifying any external state or global variables.

A key domain concept here is the strict programmatic resolution of default active learning parameters. When the non-expert engineer provides zero hyperparameter tuning options via the React GUI, the compiler mathematically generates optimized thresholds for the Two-Tier Evaluator. For instance, configuring `soft_start_steps` to 0 prevents regression when simulating simple metallic surfaces that do not require complex thermalization prior to active learning engagement. The compiler inherently understands these physical realities and embeds them into the generated configuration payload. This contrasts sharply with legacy systems that require the user to explicitly define `soft_start_steps = 0` to achieve the same result. The design philosophy is "sensible defaults, explicit overrides."

The mathematical invariants enforce strictly that every compiled `WorkflowConfig` output must natively pass all rigorous Pydantic validation checks native to the original PyAceMaker execution engine. The compiler essentially acts as a sophisticated factory method, dynamically assembling the heavily nested Pydantic models from the flattened intent representation. The design dictates that the compiler must explicitly handle every known enumeration of the `DagNode.type` field using exhaustive matching (e.g., Python 3.10+ `match...case` statements). It must raise a comprehensive `NotImplementedError` if a new, unsupported visual node is introduced to the `NodeType` enum but lacks a corresponding sub-compiler, ensuring fail-fast behaviour during development and preventing silent omissions.

The design of the Semantic Compiler also relies heavily on the concept of "Intelligent Omission." The raw `WorkflowConfig` required by the PyAceMaker core is incredibly verbose, containing dozens of configuration flags for the LAMMPS engine, the Quantum ESPRESSO DFT driver, and the MACE active learning orchestrator. The `IntentRequest` provided by the visual GUI, however, contains almost none of this information. The compiler's design dictates that it must fill in these massive blanks with domain-specific knowledge.

For example, if the user connects an `INITIAL_STRUCTURE` node containing a simple Platinum crystal directly to an `ACTIVE_LEARNING_LOOP` node, the compiler must automatically know to configure the underlying LAMMPS driver with an EAM (Embedded Atom Method) base potential for Platinum (if a zero-shot approach is not requested), specify the correct Projector Augmented-Wave (PAW) pseudopotentials for the Quantum ESPRESSO validation steps, and set a reasonable molecular dynamics integration time step (e.g., 1.0 or 2.0 femtoseconds depending on the mass of Platinum). The user never specifies these details; the Semantic Compiler infers them from the chemical context provided in the initial structure node and cross-references them against internal lookup tables. This is the essence of the "Intent-Driven" philosophy, completely abstracting the mechanical complexity of the simulation and allowing the scientist to focus purely on the thermodynamics and kinetics of their target system.

## Implementation Approach
The implementation strategy for the Semantic Compiler relies heavily on Test-Driven Development (TDD), given its pure functional nature. We will iteratively build the translation logic, starting with the simplest node transformations and gradually adding complexity, ensuring each sub-compiler is perfectly isolated and verified before moving to the next. The core of this implementation is the robust translation of a visual directed graph into a deep, nested Python dictionary that seamlessly initializes a complex Pydantic model hierarchy.

1.  **Establish Compiler Module:** Create the `compiler.py` file inside the `src/pyacemaker/domain_models/` directory. Define a central `SemanticCompiler` class containing pure mathematical translation methods that accept an `IntentRequest` instance and return a complete `WorkflowConfig` object. Ensure these functions are strictly typed using Python 3.11+ type hinting to leverage Mypy's strict static analysis. Define a custom exception class, `CompilerError`, inheriting directly from Python's base `Exception` class, to cleanly handle logical contradictions or unsupported topologies detected during the visual translation process without leaking generic Python TypeErrors or KeyErrors to the API layer.
2.  **Topological Graph Sorting:** Implement an algorithm (e.g., Kahn's algorithm or an iterative Depth-First Search approach) to perform a robust topological sort on the unordered nodes and directed edges defined in the `IntentRequest.nodes` and `IntentRequest.edges` properties. This crucial function must ensure that the directed acyclic graph drawn by the user on the 2D canvas is flattened into a strictly sequential list of operations that a state machine can execute. If the graph contains mathematical cycles (e.g., Node A points to Node B, which points back to Node A), or if the topology is fundamentally unsupported by the underlying orchestrator (e.g., multiple disconnected subgraphs floating independently, or parallel branches converging incorrectly on a single execution node), the function must immediately halt and explicitly raise a `CompilerError` detailing the exact structural invalidity (e.g., "Cycle detected between Node A (Initial Structure) and Node B (Active Learning Loop)").
3.  **DAG to Workflow Loop Mapping (Factory Implementation):** Implement the core factory logic strictly converting the topologically sorted `DagNode` list perfectly into the corresponding `LoopStrategy` sequence natively understood by the nested `WorkflowConfig` schema. Create a dispatcher function, preferably utilizing Python's `match...case` syntax, that examines the `node.type` enumeration and routes the specific node data dictionary to dedicated, highly cohesive sub-compilers (e.g., `_compile_initial_structure_node(node)`, `_compile_mace_training_node(node)`, `_compile_active_learning_node(node)`). Use exhaustive pattern matching to guarantee that absolutely no node types defined in the GUI schema are accidentally skipped or ignored during the iteration over the sorted list.
4.  **Inject Intelligent Defaults:** Within each individual sub-compiler method, ensure highly nested configuration structures like the `TwoTierEvaluatorConfig` (which governs active learning decisions) and the `LammpsDriverConfig` (which controls the C++ MD engine) receive mathematically optimized default arguments, effectively preventing immediate configuration failures upon instantiation. The compiler must hardcode sane physical defaults directly into its dictionary generation logic. For example, it must automatically inject standard convergence criteria of `1e-6` eV for DFT validations, default vacuum cell padding of `10.0` Angstroms for isolated molecules to prevent periodic image interactions, automatically assign the correct atomic masses based on the identified chemical symbols, and inject sensible barostat damping parameters of `1000.0` fs for NPT simulations. The visual user remains entirely unaware of these granular details, completely bridging the knowledge gap between intent and execution. Maintain these defaults in a centralized, easily modifiable constant dictionary within the compiler module to allow rapid updates as scientific best practices evolve.
5.  **Integrate with Endpoint:** Update the existing `POST /api/v1/intent/compile` endpoint explicitly in `api/routes/workflows.py` to accurately utilize the newly minted compiler class. The asynchronous endpoint should instantiate the compiler (or call its static translation classmethod), pass in the thoroughly validated `IntentRequest` object, and return the compiled `WorkflowConfig.model_dump()` JSON representation rather than a simple placeholder success message. This crucial step allows the React frontend to immediately verify the translation process. The developer must wrap the compilation call in a specific `try...except CompilerError` block to catch logical failures during the translation phase and correctly return an HTTP 400 Bad Request containing the specific error message extracted from the custom exception, ensuring the user understands why their specific node arrangement is physically impossible.
6.  **Implement Fallback Mechanisms:** Design the semantic compiler to gracefully handle complex edge cases where the DAG is mathematically technically valid (e.g., a completely cycle-free graph) but physically nonsensical in the context of molecular dynamics. The compiler should analyze the logical sequence of compiled states and actively raise a domain-specific `CompilerError` explaining the physical contradiction. For instance, if the topological sort yields an `ACTIVE_LEARNING` node immediately preceding an `INITIAL_STRUCTURE` node (attempting to run a simulation before defining the atoms), the compiler must reject this and return an explicit error string like "Cannot initiate active learning before defining an initial atomic structure in the workflow sequence."
7.  **Refine Type Annotations:** Ensure all internal private helper functions within the compiler module are rigorously typed using `typing.Dict`, `typing.List`, and explicit Pydantic model definitions. This is absolutely crucial for maintaining the heavily nested Pydantic models and preventing subtle dictionary assignment errors during the deeply complex transformation algorithms. Use `typing.cast` or explicit `assert` statements internally to satisfy Mypy where dynamic type resolution or nested dictionary key extraction might appear ambiguous to the static analyzer, guaranteeing absolute type safety throughout the entire compilation pipeline and preventing runtime `AttributeError` exceptions deep within the nested object generation.

## Test Strategy
The testing isolates the purely mathematical functional translation successfully, relying heavily on parameterized test inputs to cover the vast permutation space of possible GUI intents. Because the compiler is completely stateless, performs no disk I/O, and does not instantiate external binaries, these tests execute essentially instantaneously, allowing for massive, comprehensive test coverage verifying every edge case of the translation logic.

**Unit Testing Approach:**
Extensively and rigorously test the independent `compiler.py` module inside a dedicated `tests/unit/test_compiler.py` file. We will programmatically inject manually created `gui_schema.IntentRequest` instances representing typical user workflows (e.g., a simple NVE relaxation, a long NPT active learning loop with a predefined dataset) and rigorously, specifically assert that the returned `WorkflowConfig` completely matches hardcoded, highly rigorously correct expected Python configuration dictionaries cleanly. These tests must execute in under five milliseconds per assertion, as they involve zero disk reads, database calls, or network I/O.

We will specifically test the injection of intelligent defaults across multiple node types, verifying that properties like `soft_start_steps` (for gradual thermalization), `integration_timestep` (for the MD engine), and `dft_convergence_threshold` (for Quantum ESPRESSO validations) are correctly set to their established physical defaults when explicitly omitted from the minimalistic visual intent payload. For example, if the Intent payload omits the target physical temperature for a thermostat node, the unit test must explicitly assert that the compiler correctly injected exactly `300.0` Kelvin into the `LammpsDriverConfig.temperature` field deep within the nested configuration tree.

Furthermore, we will aggressively test invalid physical flows, ensuring the custom `CompilerError` is raised immediately with an appropriate, highly descriptive error message. For example, we will construct a valid, cycle-free DAG where a `MACE_TRAINING` node exists completely independently without a preceding `DATASET_IMPORT` or `INITIAL_STRUCTURE` node to provide context. The test will assert that the compiler correctly identifies this lack of required training data context during the translation phase and raises a `CompilerError`. We will comprehensively test the topological sort function using parametrized inputs, ensuring it correctly flattens complex branching structures (e.g., A -> B -> D, A -> C -> D) into a linear list or strictly rejects them with a `CompilerError` if parallel execution loops are fundamentally not supported by the underlying Python state machine. We will also test the exhaustive pattern matching by attempting to compile an Intent containing a fake, mock node type not present in the sub-compiler dispatch dictionary, verifying it strictly raises a standard Python `NotImplementedError` or a detailed `CompilerError` to prevent silent translation failures.

**Integration Testing Approach:**
Within the `tests/integration/test_api_endpoints.py` suite, we will thoroughly update the API endpoint tests to verify that the full `POST` compilation workflow successfully generates safe, deeply nested JSON correctly across the FastAPI network boundary. The integration tests will utilize the `httpx.AsyncClient` to submit a minimal Intent payload (e.g., just an initial structure and a learning loop) directly to the FastAPI endpoint and immediately assert that the resulting HTTP response body contains a JSON object that perfectly mirrors the stringent schema of the core PyAceMaker `WorkflowConfig`. This ensures the complete end-to-end translation pipeline, from the network unmarshalling of the incoming bytes, through the topological sort, to semantic compilation and default injection, functions flawlessly under realistic API load conditions.

Crucially, we will verify that the HTTP 400 Bad Request responses generated by internal `CompilerError` exceptions are properly formatted as structured JSON and returned safely to the client. This ensures the React frontend can reliably parse the error and display actionable, precise error messages to the user on the UI canvas (e.g., verifying the JSON response body explicitly contains the string `{"detail": "Cycle detected between Node A and Node B"}` rather than a generic 500 error page). This integration test acts as the final rigorous gatekeeper before development moves to Cycle 03, definitively proving that abstract visual intent can be reliably transformed into an executable, physically valid configuration payload across the network without manual intervention, and that the API securely handles all expected failure modes of the complex compilation process.
